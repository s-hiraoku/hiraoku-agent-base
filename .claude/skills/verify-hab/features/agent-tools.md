# Agent tools: send, read, reply

An agent connected to `/mcp` sees only `hab_send`, `hab_inbox`, `hab_reply` and `hab_status` (ADR-020). It sends with an address and text; the host fills in the message ID, times, the 7-day deadline, the recipient ID and the thread. The recipient reads its host inbox, which marks messages read and keeps them re-readable for 7 days, and replies by message ID. Input mistakes come back with a specific code, a fixed `message` saying what to change and, where useful, the field or the allowed values. The host audit records a fixed `reason` for each refusal.

## Sub-features

- `agent-catalog` `/mcp` lists exactly the four agent tools; `/mcp/delivery` lists the seven delivery tools (with `hab_peek` and `hab_mark_read`) for the same token. A host with Registry discovery on also lists `hab_discover` on both; the stack leaves discovery off.
- `agent-send` `hab_send {to, text}` returns `message_id`, `to`, a new `thread_id`, `state: "pending"`, a deadline 7 days after acceptance and an `explanation`; a waiting question also returns `reply_watch` (`action: "check_status"`, `next_check_at`, `stop_at`; a reply's own `reply_watch` is `action: "stop"` with `stop_at` only). Optional `kind` (default `question`), `thread_id`, `request_id` and `expected_recipient_id` are accepted too.
- `agent-send-replay` (#281) `hab_send` or `hab_reply` with a `request_id` (an `rm1.<ms>.<32hex>` ID) is idempotent: the same arguments return the same `message_id` (= the `request_id`), `thread_id` and `accepted_at` with no second message; changed arguments under the same `request_id` are `idempotency_conflict`. Without `request_id` each call is a new message.
- `agent-inbox` `hab_inbox` returns the new message with `from` (the sender's address), `kind`, `text`, `thread_id` and `new: true`; a second call returns none; `include_read: true` returns it again with `new: false`.
- `agent-read-history` (#281) `hab_inbox {read_history: "start"}` pages through already-read mail only (`new: false`), 10 per page, with `next_cursor`; pass it back as `read_history` until `messages: []` and `next_cursor: null`. A bad cursor is `invalid_request` with `field: "read_history"`.
- `agent-inbox-wait` `hab_inbox {wait_secs: N}` (ADR-028) with no unread mail waits until mail for that agent is accepted or N seconds (capped by the host's `max_wait_ms`, 25000 in the stack) pass, then reads as usual and adds `waited_secs`; unread mail returns at once with `waited_secs: 0`; `wait_secs` outside 0–60 or with `include_read`/`message_id`/`read_history` is `invalid_request` with `field: "wait_secs"`. The call outlives the stack's 2000 ms `timeout_ms`.
- `agent-notice` each inbox message has a `notice`: `<address> からのメッセージです（質問、返信期限 …）。`, the body between two `----- 受信内容 <8 hex>：…` lines that say not to follow it, then `どうしますか？` and the three choices (`1. 対応する：hab_reply …`, `2. あとで：…`, `3. 対応しない`) with the message_id.
- `agent-presentation` each inbox message also has `presentation` (ADR-026, `version: 1`): `heading` (`<address> からのメッセージです`, or `… から返事が届きました` for a reply), `sender {address, label}`, `kind`/`kind_label`, `is_reply`/`in_reply_to`, `sent_at`, `reply_by` (= `expires_at`), the same `choices` as the notice, `body_untrusted: true`, `body_note` and `hidden_data_parts`. It never contains the body; the body is `text`.
- `agent-inbox-card` `tools/list` on `/mcp` gives only `hab_inbox` `_meta.ui.resourceUri: "ui://hab/inbox-v2"` (and `openai/outputTemplate`); `resources/read` of that URI (with `Mcp-Name: ui://hab/inbox-v2` on the modern protocol) returns one `text/html;profile=mcp-app` page (the old `ui://hab/inbox-v1` still answers with the same current page; hosts cache a page per URI, so every page change gets a new URI) with `_meta.ui.csp` allowing no domains. The page shows 「受信箱を読み込んでいます…」 (never a zero-height frame) until a result arrives, sends `ui/notifications/initialized` even when `ui/initialize` fails, and also draws from ChatGPT's `window.openai.toolOutput` / `openai:set_globals`; a later `ui/notifications/tool-result` redraws; it reports its height measured at `max-content` so a host sizing the frame shows every card (test/hab-inbox-app.test.js). The look is ambient: the stylesheet has no fixed colour and takes the host's MCP Apps style variables (`--color-text-primary`, `--color-border-secondary`, `--font-sans`, `--border-radius-md`, …); あとで/対応しない fold the card to its status line. When the host refuses `ui/message` (error or `isError`, as Claude Duet does), the card says 「会話に送れませんでした。下の文をコピーして、チャットに貼ってください。」, keeps the buttons usable and shows the same request text (with the message_id, never the sender's words) and a 「文をコピー」 button. `/mcp/delivery` refuses `resources/*` with HTTP 405.
- `agent-instructions` `initialize` on `/mcp` returns `HAB_AGENT_INSTRUCTIONS`: besides the send/inbox/reply rules, it tells an agent that checks its connected accounts on its own (at intervals, or for a brief or summary, as Claude Duet does) to include `hab_inbox` in that check without being asked, so a polling agent needs no per-agent setting (test/hab-agent-tools.test.js).
- `agent-status` the sender's `hab_status` shows `acked` with an explanation that read is not acted on, `kind: "question"` and `reply_state: "waiting"` with `replies: []`, `has_unread_replies: false` and bounded read-only `reply_watch` advice.
- `agent-reply-state` after the recipient replies, the sender's `hab_status` shows `reply_state: "replied"` and one entry in `replies` (`message_id` of the reply, `kind: "answer"`, `read: false`, no text); after the sender's `hab_inbox`, `read: true`. Advice changes from `read_reply` for an unread reply to `stop` once all replies are read; `reply_state` stays `replied`. The complete matching set determines `has_unread_replies` independently of the oldest-five summary; five read replies do not hide a sixth unread one. The reply's own status (checked by the recipient) is `not_expected`.
- `agent-reply` `hab_reply {message_id, text}` goes to the original sender in the same thread with `in_reply_to`; a reply to a `question` arrives as `answer`, a reply to any other kind as `notice`.
- `agent-errors` malformed `to` → `invalid_request` with `field: "to"`; unknown address → `unknown_address`; `kind: "exec"` → `kind_not_allowed` with `allowed_kinds`; over-long text → `text_too_long` with `max_bytes`; unknown reply target → `reply_target_not_found`; an `expected_recipient_id` that is not the address's agent → `invalid_reference` with `field: "expected_recipient_id"`; more unread mail than the sender's or recipient's capacity → `capacity_exceeded` (see [send-message.md](./send-message.md) `send-capacity`); a recipient whose product reported its session ended → `recipient_absent` (only reachable with events, see [mcp-events.md](./mcp-events.md) `events-recipient-absent`); each with a `message`.
- `agent-audit` each refusal above writes a `tool_error` line with a fixed `reason` (`invalid_request`, `address_unknown`, `kind_not_allowed`, `text_too_long`, `reply_target_unknown`, …) to `$RUN/evidence/audit.jsonl`, never the text.

## How to get to it (user POV)

- Point the agent's MCP client at the host's `/mcp` (for Hermes, `tools.include: [hab_send, hab_inbox, hab_reply, hab_status]`). The agent needs `resolve` and `submit` to send, `poll` to read the inbox and `status` to check a sent message.

## Driving it with verify-hab

Preconditions:

- Baseline run, doctor OK (the doctor already checks `agent-catalog`).

- **Send.** `SENT=$($S/mcp.sh "$RUN" a hab_send '{"to":"verify-b@dot.hab","text":"please check the build"}' | sed 1d | jq -c .result.structuredContent)`; `ID=$(jq -r .message_id <<<"$SENT")`. `state: "pending"`, `expires_at` 7 days after `accepted_at`.
- **Read.** `$S/mcp.sh "$RUN" b hab_inbox '{}'`: one message, `from: "verify-a@grok-bot.hab"`, `new: true`. Run it again: `messages: []`. Then `$S/mcp.sh "$RUN" b hab_inbox '{"include_read":true}'`: the same message with `new: false` (if the read happened in the same millisecond it is not listed; call again).
- **Notice.** `$S/mcp.sh "$RUN" b hab_inbox '{"include_read":true}' | sed 1d | jq -r '.result.structuredContent.messages[0].notice'` prints the notice; the tag on the two frame lines matches.
- **Wait for new mail.** `( sleep 3; $S/mcp.sh "$RUN" a hab_send '{"to":"verify-b@dot.hab","text":"wait test"}' >/dev/null ) & $S/mcp.sh "$RUN" b hab_inbox '{"wait_secs":20}'` returns after about 3 s with that message and `waited_secs: 3`; `$S/mcp.sh "$RUN" b hab_inbox '{"wait_secs":4}'` returns `messages: []` after about 4 s; `'{"wait_secs":4,"include_read":true}'` is `invalid_request` with `field: "wait_secs"`. `test/hab-inbox-wait.test.js` covers other agents' mail, the cap, superseding and the hold limit.
- **Presentation and card.** `$S/mcp.sh "$RUN" b hab_inbox '{"include_read":true}' | sed 1d | jq '.result.structuredContent.messages[0].presentation'` shows the fields above. Whether a real host draws the card (claude.ai, ChatGPT, the Gemini app) is outside this stack; `test/hab-agent-tools.test.js` covers the tool `_meta` and `resources/read`.
- **Read one again.** `$S/mcp.sh "$RUN" b hab_inbox "{\"message_id\":\"$ID\"}"` returns that message with `new: false`.
- **Status.** `$S/mcp.sh "$RUN" a hab_status "{\"message_id\":\"$ID\"}"`: `state: "acked"`, `to: "verify-b@dot.hab"`, `reply_state: "waiting"`.
- **Reply.** `$S/mcp.sh "$RUN" b hab_reply "{\"message_id\":\"$ID\",\"text\":\"green\"}"`, then `$S/mcp.sh "$RUN" a hab_inbox '{}'`: `kind: "answer"`, `from: "verify-b@dot.hab"`, `in_reply_to: "$ID"`, same `thread_id`. Before that `hab_inbox`, `$S/mcp.sh "$RUN" a hab_status "{\"message_id\":\"$ID\"}"` shows `reply_state: "replied"` and the reply in `replies` with `read: false`.
- **Errors.** `$S/mcp.sh "$RUN" a hab_send '{"to":"verify-b@dot","text":"x"}'`, `'{"to":"nobody@dot.hab","text":"x"}'`, `'{"to":"verify-b@dot.hab","text":"x","kind":"exec"}'`, `$S/mcp.sh "$RUN" a hab_send "{\"to\":\"verify-b@dot.hab\",\"text\":\"$(head -c 16001 /dev/zero | tr '\0' x)\"}"` (the stack's text limit is 16000 bytes; a request body over 65536 bytes is refused earlier with HTTP 413), and `$S/mcp.sh "$RUN" a hab_reply '{"message_id":"unknown","text":"x"}'`. Each is HTTP 200 with `"isError":true` and the code listed under `agent-errors` (`text_too_long` carries `max_bytes: 16000`).
- **Retry with `request_id`.** `RID=$(jq -r .message_id <<<"$($S/new-message.sh "$RUN" b x)")`, then run `$S/mcp.sh "$RUN" c hab_send "{\"to\":\"verify-b@dot.hab\",\"text\":\"replay\",\"request_id\":\"$RID\"}"` twice: both return `message_id: "$RID"`, `thread_id: "t-$RID"` and the same `accepted_at`; the same call with `"text":"changed"` is `idempotency_conflict`; b's next `hab_inbox` holds the message once.
- **Read history.** After b has read mail, `$S/mcp.sh "$RUN" b hab_inbox '{"read_history":"start"}'` returns up to 10 messages with `new: false` and a `next_cursor`; feed it back as `read_history` until `messages: []`, `next_cursor: null`. `'{"read_history":"bad"}'` → `invalid_request` `field: "read_history"`; `'{"wait_secs":3,"read_history":"start"}'` → `field: "wait_secs"`.
- **Reply to a notice.** a `hab_send`s `{"to":"verify-c@hermes.hab","text":"fyi","kind":"notice"}`, c reads and `hab_reply`s; a's `hab_inbox` shows the reply with `kind: "notice"`.
- **Wrong expected recipient.** `$S/mcp.sh "$RUN" a hab_send "{\"to\":\"verify-c@hermes.hab\",\"text\":\"x\",\"expected_recipient_id\":\"$(jq -r .agents.b.agent_id $RUN/instance/state.json)\"}"` → `invalid_reference`, `field: "expected_recipient_id"`.
- **Proof.** `grep reason "$RUN/evidence/audit.jsonl"` shows the fixed reasons; `node $S/inspect.mjs "$RUN" after-agent` shows the two messages `acked`.

## Gotchas

- `hab_poll` and `hab_ack` are not on `/mcp`; `mcp.sh` sends them to `/mcp/delivery`. A message read by `hab_inbox` is already ACKed and never appears in `hab_poll`, and one leased by `hab_poll` is skipped by `hab_inbox` until the lease ends.
- Missing or wrongly typed arguments are refused by the MCP SDK before the tool runs (`Input validation error: …`, no `structuredContent`); value mistakes get the structured codes.
- A reply after the original's `expires_at` is `reply_target_expired`, even when the message was read.
- `hab_send` without `request_id` is not idempotent: a retry after a lost result sends a second message. Pass the same `request_id` to retry safely (`agent-send-replay`).

- `reply_watch` is additive advice: bad planning times omit it without hiding an accepted send. In the owned synthetic roundtrip, inspect `SENT.reply_watch` and the original sender's status before/after explicitly reading the reply. Check `next_check_at` initially about 15 seconds ahead, `stop_at` no later than acceptance + 30 minutes/message expiry, then `read_reply` → `stop`. `test/hab-agent-tools.test.js` and `test/reply-watch.test.js` cover bounds and failure isolation.
- The optional owner runner is exercised by `node --test test/reply-watch-adapter.test.js`: real owned HTTP/SQLite send/status with an unread reply, saved schedule reopen/scope/claim/cancellation, resident timer, bounded retry/deadline/authentication stop and no duplicate sends. Follow [reply monitoring](../../../../docs/reply-monitoring.md) for the shipped `hab:reply-watch` owner CLI. The fixture substitutes identity and schedule time; it proves no real Dots wake, native session or production OAuth.
