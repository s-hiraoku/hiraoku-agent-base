# New-mail events for cloud agents

A cloud agent such as Dots (ChatGPT) subscribes, over its own OAuth connection to the ingress `/mcp`, to the MCP event `hab.message.received` (ADR-022). When mail arrives for it, HAB POSTs a signed Standard Webhooks doorbell to the subscribed public HTTPS callback carrying only `{to, arrived_at}`; the agent still reads the mail with its own `hab_inbox`, and the doorbell marks nothing read. Off unless the host config has `ingress.events`.

## Sub-features

- `events-capability` with `ingress.events`, `initialize` on the ingress `/mcp` advertises `capabilities.events`; `events/list` returns one event `hab.message.received` with an empty `inputSchema` and a payload of `to` and `arrived_at` only. Without `ingress.events`, on `/mcp/delivery` and on loopback, the HTTP admission refuses `events/*` with 405 and no `events` capability is advertised.
- `events-subscribe` `events/subscribe {name, arguments:{}, delivery:{mode:"webhook", url, secret:"whsec_…"}, ttlMs}` first POSTs a signed `{"type":"verification","challenge"}` and subscribes only when the same challenge comes back; it returns `{id:"hab_sub_…", refreshBefore, cursor:null, truncated:false}`. The same connection and URL get the same `id`; resubscribing replaces the secret and resets the lifetime to now + `ttlMs` (clamped to 60 s – `max_ttl_ms`), so a smaller `ttlMs` shortens it. Refusals carry `data.reason`: `unknown_event`, `invalid_arguments`, `invalid_params`, `unsupported_delivery`, `invalid_secret`, `invalid_callback_url`, `too_many_subscriptions` (-32602); `callback_not_public`, `challenge_failed`, `timeout` (-32015).
- `events-doorbell` each new unread message sends one POST per subscription with `webhook-id` = `eventId`, `webhook-timestamp`, `webhook-signature: v1,<base64 HMAC-SHA256 of id.timestamp.body>` and `X-MCP-Subscription-Id`; the body has no text, sender, kind or message ID, and the message stays `pending` until `hab_inbox`.
- `events-retry` a non-2xx is resent with the same `eventId` (up to 8 attempts; the wait is `2 s × 2^failures` capped at 5 min, so the first retry comes after 4 s, then 8 s, 16 s, …); 413 or the 8th failure moves on; 410 deletes the subscription. Expired subscriptions and `events/unsubscribe` stop delivery.
- `events-store` subscriptions live in `<state>/events.sqlite`, owner-only (0600); it holds the webhook secrets.
- `events-outage` (ADR-024) the dispatcher stamps a clock every tick, also while a slow pass runs. A gap longer than `outage_after_ms` (default 60 s, never below 3 polls so ordinary ticks never extend lifetimes; config 1000–86400000) means the host was stopped or the Mac slept: subscriptions alive when the gap began get the gap added to their lifetime, at most `max_ttl_ms`. A subscription that had already expired while ticks were running is not revived.
- `events-lapse` (ADR-024) a subscription ending by expiry, 410 or `events/unsubscribe` records the recipient's last `lapsed_at` and reason (`expired`/`gone`/`unsubscribed`); subscribing again clears it. `hab:admin status` → `inboxes[]` shows `unread`, `oldest_unread_at`, `doorbell` (`live`/`lapsed`/`none`/`off`) and adds `problems` `unread_waiting` (unread ≥ 30 min) and `doorbell_lapsed`, without callback URLs or secrets. Once a recipient has been rung it also shows `doorbell_last_rang_at`, `doorbell_last_status` (the callback's HTTP status, `0` for no answer) and `doorbell_last_delivered_at` (last 2xx), with `doorbell_failing` when the latest ring was not 2xx. HAB never re-creates a subscription itself.
- `events-operator` (ADR-029) `ingress.events.doorbells: [{address, url, secret_file}]` registers a doorbell per address at host start: same `{to, arrived_at}` body and retry/ring-again rules, `Authorization: Bearer <token>` when the secret is not `whsec_` (16–512 chars), Standard Webhooks signature when it is; no challenge, no lifetime, no subscriber slot, not removable by `events/unsubscribe`; mail already waiting at start is not rung. Unknown address → start refused `unknown_doorbell_address`; non-public or non-HTTPS URL or weak secret → `invalid_doorbell`; secret file not owner-only/regular/≤1 KiB → `unsafe_doorbell_secret`. `hab:admin status` shows `doorbell: "live"` and `doorbell_operator` without URL or secret. Covered by `test/hab-events.test.js`, `test/host-oauth.test.js`, `test/host-service.test.js` and `test/host-admin.test.js` (the stack has no ingress).
- `events-unanswered` (ADR-027) a doorbell accepted with a 2xx whose message is still unread `unanswered_after_ms` later (default 5 min, config 60000–86400000) is rung once more on the same subscription with a different `eventId` and the same `{to, arrived_at}`; never retried, and off with `ingress.events.rering: false`. The recipient's own `/mcp` results of `hab_send`, `hab_reply` and `hab_status` carry `inbox_reminder` `{unread, more, oldest_unread_at, doorbell_delivered_at, doorbell_unanswered, explanation}` (`doorbell_delivered_at` is the earliest first 2xx acceptance among the unread messages, so a second ring or newer mail never hides an older unanswered one) while its mail waits unread; `hab_inbox` carries it only when the doorbell went unanswered (computed before the read). Unread is counted from the caller's own authorization-filtered peek, so mail from a sender it may no longer read never keeps a reminder alive. No body, sender or message ID. The agent `instructions` tell it to call `hab_inbox` on the event and follow `inbox_reminder`.
- `events-quiet` (ADR-030) per subscription HAB remembers the last doorbell accepted with a 2xx. While it is younger than `unanswered_after_ms` and its message is still unread, newer mail is not rung: it is held behind the cursor (not skipped), so it rings when the quiet ends if still unread, and never if it was read (reading only the rung message ends the quiet at the next pass). Each pass runs the ADR-027 ring again first (at most ten per pass; a subscription whose ring again is due but left for the next pass also holds its new mail, only while `rering` is on), and an accepted ring again starts a new quiet, so an unread inbox gets about one ring per `unanswered_after_ms`. Non-2xx answers never start a quiet, and a message mid-retry is not held. `ingress.events.quiet: false` rings every message.
- `events-recipient-absent` (ADR-032, PR-7) only a doorbell answered `410` with body `{"reason":"session_gone"}` counts; `ingress.events.absent_after` (default 3, 1–20) such answers in a row mark the address absent in `events.sqlite` (`hab_event_absent`), and session_gone mail is not resent. No answer, 5xx, any other 4xx and a 410 without that reason never count (a plain 410 still ends the subscription). Then `hab_send` to that address (also its previous name, and also on the loopback `/mcp` that offers no events) is refused with the public error `recipient_absent` — checked after the caller's own resolution, so an unknown/blocked recipient still answers `unknown_address`. A 2xx from the product, or a new subscription (not a refresh) or a newly registered operator doorbell, clears it. `hab:admin status` adds `problems` `recipient_absent` and `inboxes[].recipient_absent_since`. The ledger row and unread mail are kept.
- `events-inbox-check` retired by ADR-032: HAB no longer rings on a timer. A doorbell rings for new mail and once more after `unanswered_after_ms` (ADR-027), never again. An old config with `ingress.events.inbox_check` still starts; the host's `ready` line carries `"ignored_config":["ingress.events.inbox_check"]`. Each `hab_inbox` call records the reader's time in `events.sqlite` (`hab_event_inbox_reads`); `hab:admin status` shows it as `inboxes[].last_inbox_read_at` and, for a product set to `receive --mode poll`, reports `poll_overdue` once two intervals pass since the later of that read and the setting.

## How to get to it (user POV)

- Operator adds `"events": {}` to the host `ingress` config and restarts ([MCPイベントで新着を知らせる](../../../../docs/connections/mcp-events.md)). The user reconnects the ChatGPT connector and asks Dots to run a task on `hab.message.received` that calls `hab_inbox`. Muse has no events; it uses its own scheduled task calling `hab_inbox`.

## Driving it with verify-hab

- The verify-hab stack starts only the loopback catalogs, which never offer events, and has no OAuth issuer or public HTTPS callback. Check the absence there: a raw JSON-RPC POST of `events/list` to `/mcp` → HTTP 405.
- Everything else is covered by unit tests with an injected HTTPS poster and an in-process OAuth ingress: `node --test test/hab-events.test.js` (signature vector, SSRF refusals, capability and list, verification and idempotency, challenge failure, doorbell without content with the message still unread, retry/backoff/410, expiry and unsubscribe, owner-only store, outage credit and its cap, lapse records, latest ring status, a slow pass is not an outage, the second ring for an unanswered doorbell and `inbox_reminder`, newer mail held while an accepted doorbell is unread, no timer ring after the ring again, the session_gone absence count, the answers that never count and the loopback refusal, restart, no-retry and per-agent off) and `node --test --test-name-pattern "ingress events" test/host-oauth.test.js` (the configured ingress advertises and answers events; the loopback and delivery catalogs do not).
- A live check needs a public HTTPS receiver and a real OAuth agent connection; do it only in an owner-authorized acceptance run (for example Dots on the Mac mini), never with a callback this run does not own.

## Gotchas

- The doorbell is not delivery. Never assert on mail content from a webhook; read it with `hab_inbox` as the subscribed agent.
- Callbacks to private, loopback, link-local, mapped or `.local`/`.internal` names are refused before any request, so a local test receiver cannot be used without the injected poster.
- Whether ChatGPT actually starts work on an event, and how late, is ChatGPT's decision; HAB only proves it sent a signed POST.
- `recipient_absent` cannot be produced on the verify-hab stack or the configured host: it needs a doorbell, which needs a public HTTPS callback. Run `node --test --test-name-pattern "session_gone|absent|session ended" test/hab-events.test.js test/host-admin.test.js` (4 tests: absent after three answers and `hab_send` refused, non-counting answers, the loopback endpoint, and the `status` view). A live check means a product endpoint you own answering `410 {"reason":"session_gone"}`, in an owner-authorized run.
- Outage credit cannot be shown on the verify-hab stack (no events there). It is unit-tested with an injected clock; `node --test --test-name-pattern "unread mail waiting" test/host-admin.test.js` covers the `inboxes` view on a configured host. On a live host, check `hab:admin status` for `doorbell_lapsed` after the host was down.
