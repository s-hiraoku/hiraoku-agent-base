# Configured host and operator CLI

The shipped host (`npm run hab:host -- --config …`) refuses a bad start with a fixed reason line, and the operator CLI (`npm run hab:admin -- --config … status|doctor|pending|approve|reject|revoke|doorbell add/remove/list|recipe|ping|connect|disconnect|rename|receive|session`; `rename` is driven in [resolve-address.md](./resolve-address.md)) registers an address, binds a mapped connection, grants operations and revokes it again — all against the same private config while the host runs. This is the path a real Codex ⇄ Hermes trial uses, unlike the `stack.mjs` scaffolding.

## Sub-features

- `start-reason` a refused start prints `host_start_rejected reason=<code>[ fields=<paths>]` (e.g. missing `delivery.queue.agent_capacity` → `reason=config_invalid fields=delivery.queue.agent_capacity`), never values or paths.
- `retired-config` a config that still has the retired SQLite `store` section (and no `delivery`) is refused with `reason=config_invalid fields=delivery,store` before any state is created.
- `admin-connect` `connect --address <a> --connection-id <id>` registers product/address, creates the connection's authentication group (the address is its only member), binds and grants; rerun returns `steps: []`.
- `admin-receive` `receive --agent-name <product> --mode hook|poll|on_request [--interval-ms <60000..86400000>] --request-id <id>` sets how a product hears about new mail (ADR-032). `interval_ms` goes only with `poll`; anything else is `invalid_registry_request`, an unknown product `registry_not_found`. `status.products[]` shows `{agent_name, receive}` (`receive: null` until set).
- `admin-session` `session --address <a> --session <name> [--replace true] --request-id <id>` names the product session the address stands for. Every address starts as a provisional session named after itself (`session.provisional: true`); a named one is not replaced without `--replace true` (`registry_session_bound`), and two addresses of one product never share a name (`registry_session_taken`). Provisional names are not unique, so an operator name never blocks a later address from enrolling. A provisional session follows a rename to the new address, and each start corrects a provisional session still named after an old address (a named one is never touched); `session --address` looks the address up by exact match. A registry from before ADR-032 makes `status` answer `registry_upgrade_pending` until the host starts once.
- `admin-status` `status` lists addresses, credential lifetime/audience/binding and `problems` (`credential_unbound`, `credential_expired`, `credential_audience_mismatch`, `credential_revoked`, `address_unbound`, `address_stopped`). Since ADR-024 it also lists `inboxes[]` per active address (`unread`, `oldest_unread_at`, `doorbell` live/lapsed/none/off) with `unread_waiting` (unread ≥ 30 min) and `doorbell_lapsed` problems, plus `doorbell_last_rang_at`/`doorbell_last_status`/`doorbell_last_delivered_at` and a `doorbell_failing` problem once a recipient has been rung. `configured.sh` writes no `ingress`, so `doorbell` is always `off` there and `unread_waiting` is out of reach within the credentials' 15 minutes; the live check is `unread: 1` with an `oldest_unread_at` for a submitted, unpolled message. Status also lists other problems (`participation_*`, `group_<state>`, `config_previous_address*`, `emergency_stopped`) not driven here.
- `admin-doctor` `doctor [--address <a>]` reads `status` only and writes nothing. With `--address` it answers `{address, checks}` where `checks` has `registration`, `receive`, `reading` and `session`, each `{state: ok|problem|unknown, reason, evidence, next_action}` (`next_action` is Japanese text, `null` when nothing is to do). Without it, one line per address with each check's state and `first_problem` (`<check>:<reason>`). Reasons include `address_unbound`, `operations_missing`, `approval_expired`/`approval_expiring` (≤ 14 days), `receive_unset`, `doorbell_missing`/`doorbell_lapsed`/`doorbell_failing`/`events_off`, `poll_overdue`/`poll_never_read`/`reads_untracked` (events off), `rang_not_read` (a 2xx ring after the oldest unread mail, an address seen reading with `hab_inbox` but not since, over 2 minutes; a notifier reads through the delivery tools and never gets it), `unread_waiting`, `waiting_for_request` (on_request) and `recipient_absent`; `session` is otherwise `unknown:session_not_reported`. An unknown address is `address_not_found`, a malformed one `invalid_address`, any other flag `usage`. Reason-by-reason coverage is `test/host-doctor.test.js` (synthetic status) plus a running-host case that compares every table of the three stores before and after.
- `admin-pending` (plan 2) a sign-in that passes every OAuth check but the ledger (signature, issuer, audience, scope, lifetime) is kept in `<state>/oauth-pending.sqlite` (0600; `pending_id`, issuer, subject, client_id, first/last seen, attempts; no token) and still refused with the same reason (`client_not_registered`/`subject_not_registered`). Forged, expired, too long-lived or out-of-scope tokens are not kept. At most 32 rows, gone 14 days after last seen; when full a stranger's oldest row goes first and a subject already in the ledger is never pushed out by a stranger. `pending` lists rows with the subject masked; `status.pending_connections` counts them and doctor's `registration` becomes `pending_approval` for an address with no working connection. `approve --pending <id> --address <a> [--days 1..3650]` backs the ledger up (`<ledger>.bak-<time>-<uuid>`, 0600), adds one v2 row (`approved_at` now, never earlier) through a temp file and rename, binds the connection without changing the group's or the address's access state or operations when the address already belongs to a group, including a stopped group (`connect.steps: ["connection_bound"]`), and removes the row. One approve at a time edits the ledger (`<ledger>.approve-lock.sqlite` holds a SQLite write lock; process exit releases it, and a competing approve, reject, revoke or connect on a host with OAuth ingress waits up to 5 s before `ledger_busy`). A ledger that would exceed the host's 65,536-byte config limit is never written (`ledger_too_large`, no backup, the row stays pending); a pair already in the ledger is reused (`ledger: "existing"`, no backup), so a repeat never duplicates it. A token issued before the approval stays `token_before_approval`; a later one works with no restart. `reject --pending <id>` uses the same lock and removes a row (`invalid_pending_id` for a malformed ID). `configured.sh` has no ingress, so these answer `oauth_not_configured` there; coverage is `test/oauth-pending.test.js` and the "plan 2" cases of `test/host-participation.test.js` (a real host and ingress).
- `admin-recipe` (plan 4) `recipe` lists the product recipes in `config/products/` (`antigravity`, `claude-ai`, `dots`, `grok`, `hermes`, `muse`) with their receive mode; `recipe --product <p> [--address <a>] [--allowed <a>] [--conversation <c>]` prints one with the guide's placeholders filled (the product name comes from the address) and lists the ones left `unfilled`. It reads no host state, so it works without a running host. An unknown or malformed product name is `unknown_product`, a bad address `invalid_address`, a recipe that breaks the schema `invalid_recipe`. `test/product-recipes.test.js` also holds each recipe to its section of `docs/connections/agent-setup.md` (heading and agent prompt word for word) and checks it carries no secret, token, Webhook URL or real address.
- `admin-doorbell` (plan 3) `doorbell add --address <a> --url <url> --secret-file <path>` / `remove --address <a>` / `list` keep the operator doorbells in the Registry; behaviour and errors are in [mcp-events.md](./mcp-events.md) `events-operator-registry`. Every form needs `ingress.events`, so on `configured.sh` (no `ingress`) each answers `admin_rejected events_not_configured`.
- `admin-ping` (#281) `ping --address <a> [--wait 0..60] [--request-id <rm1 id>]` sends one fixed test notice (`HAB の接続確認です。…`) from the host config's `operator_mail.ping` identity (`{address, agent_id, bearer_file}`; the bearer file is `{"version":1,"bearer":"…"}`, owner-only) and answers `{operation_id, message_id, to, state, accepted_at, acked_at, read_at, doorbell_at, reply_at, problem}`; without `--request-id` it prints `ping_request_id <id>` on stderr first. `ping --status <operation_id>` reads it again (`acked`, `read_at` once the recipient read it). No `operator_mail.ping` → `operator_mail_not_configured`; no fixed `port` → `operator_mail_requires_fixed_port`; an unknown address → `unknown_address`. Details: `docs/host-service.md`「CLI の試験送信とダッシュボードの送受信」.
- `dashboard` (#281) `npm run hab:dashboard -- --config <cfg> [--operator]` starts a loopback page and prints the path of an owner-only `open-dashboard.html` launcher. Its form POSTs the launch value to `/session` (only `Origin: null`, as a browser sends from a file), which returns the page with a `hab-session` bearer and `hab-role` (`viewer`, or `operator` with `--operator`). `GET /api/diagnostics` with that bearer lists the addresses with the doctor checks; without it → 401, with `Host: localhost:<port>` → 403; a viewer's `POST /api/mail/*` → 403. Mail send/reply/inbox needs `operator_mail.mailbox`. `test/hab-dashboard.test.js` covers the rest.
- `admin-disconnect` `disconnect --address <a>` revokes with current epochs; works after the token mapping was deleted; rerun → `already_disconnected: true`; the old token then gets `forbidden`.
- `group-disconnect` disconnecting one member of a shared connection stops **every** member (`state: stopped`, `operations: []`) and lists them in `affected_addresses`. Reconnecting one address with a new connection id re-grants only that address; its sibling stays `stopped` and polling as it is `forbidden`. A poll without `as_address` selects the only active member.
- `admin-revoke` (DCR plan 6) `revoke --connection <connection_id>` stops one OAuth connection and leaves the group's other connections live (`disconnect` revokes all of them). Under the same `<ledger>.approve-lock.sqlite` lock as approve and connect on a host with OAuth ingress, it checks the private file and its configured ingress resource, backs the ledger up (0600) and sets that v2 row to `state: "revoked"` through a temp file and rename, so its tokens are refused at once (401) with no restart; then it revokes that connection's one Registry binding. The result is `{ledger: "revoked"|"already_revoked", backup, registry: {binding: "revoked"|"already_revoked"|"none", group_id, group_state, remaining_active_bindings}}`; a rerun after a stop half way finishes the missing step. Revoking the group's last live binding stops the group (`group_state: "stopped"`). `connection_not_found` for an ID not in the ledger, `invalid_connection_id` for a malformed one, `oauth_ledger_not_v2` for a v1 ledger. A mismatched resource is `oauth_resource_mismatch` before any write. An approve and revoke can run concurrently without losing changes. Connect cannot bind a revoked row. Coverage is the "DCR plan 6" cases of `test/host-participation.test.js`; `configured.sh` has no ingress (`oauth_not_configured`).
- `admin-refusals` `connect … --operations ""` → `admin_rejected invalid_operations`; a group connect refused by binding capacity creates no group (a retry converges); a config that still says `registry.authentication_groups: false` connects through a group all the same; a registry an earlier build left with direct bindings is refused with `registry_upgrade_pending` until the host starts once.
- `registry-limits` an out-of-range `registry.*` limit (e.g. `busy_timeout_ms` above 1000) is refused at start with `reason=config_invalid fields=registry.<field>`.
- `configured-roundtrip` a → b submit / poll / ack / sender status `acked` through the shipped host and its SQLite delivery store. A submit with an `attachment` part is refused (`isError`, nothing stored), as in `send-attachment-refused`.
- `host-exact` `Host: localhost:<port>` → HTTP 403; only `127.0.0.1:<port>` is accepted.

## How to get to it (user POV)

- Operator shell: `npm run hab:host -- --config <service.local.json>` and `npm run hab:admin -- --config <service.local.json> <command>`.
- Agents: each agent's MCP client at `http://127.0.0.1:<port>/mcp` with its own bearer.

## Driving it with verify-hab

Preconditions:

- `npm ci` with Node ≥ 26. A fresh `RUN=/tmp/hab-verify/<id>` (do not reuse a stack.mjs run dir).

- **Start.** `$S/configured.sh "$RUN" start` writes example-based config, random keys and two synthetic 15-minute credentials under `$RUN/instance/`, fills `delivery.volume` for `instance/state`, starts `scripts/hab-host.ts`, runs `hab:admin connect` for `a` = `codex@codex.hab` and `b` = `hermes@hermes.hab`, and prints `CONFIGURED_READY <url>`. `instance/state.json` has the same shape as the stack's, so `mcp.sh` and `new-message.sh` work unchanged. Connect output is saved as `evidence/admin-connect-{a,b}.json` (`steps` lists what was created).
- **Roundtrip.** Use the minimal round trip from `SKILL.md` with agents `a` and `b` (target `hermes@hermes.hab`). Sender `hab_status` ends `"acked"`. `instance/state/` holds `delivery.sqlite` and no `relay.sqlite` or `jetstream-journal.sqlite`.
- **Status.** `$S/configured.sh "$RUN" admin status` → `problems: []` while both are connected. Between the submit and the poll of the roundtrip, `jq '.inboxes'` shows `hermes@hermes.hab` with `unread: 1`, an `oldest_unread_at` and `doorbell: "off"`.
- **Receive and session.** `$S/configured.sh "$RUN" admin receive --agent-name hermes --mode poll --interval-ms 60000 --request-id r1` → `receive.mode: "poll"`, `interval_ms: 60000`. `$S/configured.sh "$RUN" admin session --address hermes@hermes.hab --session desk --request-id s1` → `session.provisional: false`. `admin status` shows both under `products[]` and the address's `session`; a second `session … --session other --request-id s2` answers `admin_rejected registry_session_bound`.
- **Doctor.** After **Receive and session**, `$S/configured.sh "$RUN" admin doctor` lists `codex@codex.hab` and `hermes@hermes.hab`; `admin doctor --address hermes@hermes.hab` → `checks.receive.reason: "reads_untracked"` (poll set, but with no `ingress.events` HAB records no inbox reads) and `codex@codex.hab` → `first_problem: "receive:receive_unset"` and `checks.registration.state: "ok"`. `configured.sh` writes no `ingress`, so a Hook product shows `events_off` here.
- **Doorbell refused.** `$S/configured.sh "$RUN" admin doorbell list` → `admin_rejected events_not_configured`.
- **Recipe.** `$S/configured.sh "$RUN" admin recipe | jq -r '.products[].product'` → `claude-ai dots grok hermes muse`; `admin recipe --product hermes --address hermes@hermes.hab | jq .unfilled` lists the placeholders still open; `--product nope` → `admin_rejected unknown_product`. `admin pending` and `admin revoke --connection <id>` → `admin_rejected oauth_not_configured`.
- **Ping.** `admin ping --address hermes@hermes.hab` first → `operator_mail_not_configured`. Then `configured.sh stop`, write `instance/ping-bearer.local.json` (0600) as `{"version":1,"bearer":"<a's token>"}`, add `"operator_mail":{"ping":{"address":"codex@codex.hab","agent_id":"<a's agent_id>","bearer_file":"<abs path>"}}` to `service.local.json` (0600) and `configured.sh restart`. `admin ping --address hermes@hermes.hab` → `state: "pending"`; b's `hab_inbox` shows a `notice` from `codex@codex.hab`; `admin ping --status <operation_id>` → `state: "acked"` with `read_at`; `--address nobody@hermes.hab` → `admin_rejected unknown_address`.
- **Dashboard.** With the host running, start `node scripts/hab-dashboard.ts --config "$RUN/instance/service.local.json"` in the background and record its pid. Read the launcher path it prints, take the form's `action` and `launch` value, `curl -X POST <action> -H 'Origin: null' --data-urlencode launch=<value>` and read the `hab-session` meta. `curl <base>/api/diagnostics -H "Authorization: Bearer <it>"` lists both addresses; no bearer → 401; `Host: localhost:<port>` → 403; `POST /api/mail/ping` as viewer → 403. Stop it by that pid (SIGTERM).
- **Disconnect.** `$S/configured.sh "$RUN" admin disconnect --address hermes@hermes.hab` → `revoked_bindings: 1`; again → `already_disconnected: true`; `$S/mcp.sh "$RUN" b hab_poll '{}'` → `{"error":"forbidden"}`; `status` shows `credential_revoked` and `address_stopped`.
- **Group disconnect.** Start a separate run with `HAB_VERIFY_GROUPS=1 $S/configured.sh "$RUN" start`: `state.json` has an unconnected spare credential `c` (`.agents.c.connection_id`). Read `a`'s connection id from `admin status` (`.credentials[] | select(.addresses == ["codex@codex.hab"]) | .connection_id`), then `admin connect --address second@codex.hab --connection-id <it>` → `steps: [address_enrolled, group_member_added, address_access_granted]`. `admin disconnect --address second@codex.hab` → `affected_addresses` both, and `admin status` shows both `stopped` with `operations: []`. `admin connect --address codex@codex.hab --connection-id <c's id>` → `steps: [connection_bound, group_access_granted, address_access_granted]`; then `$S/mcp.sh "$RUN" c hab_poll '{"as_address":"second@codex.hab"}'` → `forbidden`, `as_address` codex and an empty selector → `{"delivery":null}`.
- **Start reason.** Copy `instance/service.local.json` to `instance/bad.local.json` (0600) with `delivery.queue.agent_capacity` removed and run `node scripts/hab-host.ts --config "$RUN/instance/bad.local.json"`: exit 1, the single stderr line above.
- **Legacy journal.** Stop, `touch instance/state/jetstream-journal.sqlite` (0600) and start again with `node scripts/hab-host.ts --config "$RUN/instance/service.local.json"`: exit 1, `host_start_rejected reason=legacy_jetstream_journal_present`. Remove the file before continuing. A config with `delivery.broker` or `delivery.pump` is refused with `reason=config_invalid fields=delivery.broker` (or `delivery.pump`).
- **Retired config.** `jq '.store = .delivery.queue | del(.delivery) | .port = 0' instance/service.local.json > instance/old.local.json` (0600), then start with it: exit 1, `host_start_rejected reason=config_invalid fields=delivery,store`.
- **Host.** `curl -s -o /dev/null -w '%{http_code}' -H "Host: localhost:<port>" -H "Authorization: Bearer $(jq -r .agents.a.token "$RUN/instance/state.json")" -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' "$(jq -r .url "$RUN/instance/state.json")" -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'` → `403`.
- **Stop.** `$S/configured.sh "$RUN" stop` stops the host (by pid + cmdline) and prints `stopped <pid>`. It leaves `$RUN/instance`; run `rm -rf "$RUN/instance"` yourself afterwards. `evidence/host.log` keeps `ready`/`stopped`.

## Gotchas

- `inspect.mjs` and `doctor.sh`/`cleanup.sh` target the stack layout; use `configured.sh … admin status` and `configured.sh … stop` here.
- An accepted message is pollable at once; `{"delivery":null}` right after a submit means the recipient already holds a lease or the message is not addressed to it.
- If `start` fails after the host came up, run `configured.sh "$RUN" stop` anyway.
- Credentials expire 15 minutes after `start`; after that every call is 401 and `status` shows `credential_expired`. Relaunch with a new run dir.
- A group stop or its last disconnect stops every member; reconnect each member address you still want (one `connect` per address).
- A revoked connection id can never be bound again (`credential_revoked_use_new_connection_id`); a new credential needs a new `connection_id`.
- `limits` no longer has `attachment_bytes`, `total_attachment_bytes` or `attachments`. A config that still carries any of them is refused at start with `reason=config_invalid` and `fields=` listing each unrecognized key (for example `limits.attachment_bytes`, or all three sorted). Delete those keys.
- `hab:dashboard` is not stopped by `configured.sh stop`; kill the pid you started. Its temporary `/tmp/hab-dashboard-*` launcher dir goes away when it stops.
- Tokens are synthetic and local; a pass is not evidence of a real Codex/Hermes client or model choosing tools.
