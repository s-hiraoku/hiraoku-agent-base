# Operate one private Linux host

## Select the data volume

Choose a persistent volume and a dedicated service account before deployment. No provider, billable server, or OS service is created by this implementation.

Put the canonical private service state directory on that volume. Store `volume.local.json` directly inside it with the configured logical `volume_id`. Record the directory's `stat.dev` as `volume.expected_device` on that host. Do not copy a marker onto an underlying fallback directory.

The host validates the marker location, logical ID, file privacy, and device before creating state files. It repeats the storage check before commits and pump cycles. A missing or changed volume stops those operations. These checks do not constitute a physical unplug or power-failure test.

Use separate named files for Registry, NATS admission journal, Task Store, and recipient checkpoints. Keep the broker store on the selected persistent volume. A state directory from the retired SQLite delivery store may still contain `relay.sqlite`. The host starts without a warning, ignores the file and never migrates or delivers its messages. Before upgrading, check each state directory for `relay.sqlite`: any message still pending in it is lost to recipients unless its sender resends it. Reconcile those senders first, then archive or delete the file.

## Configure the private broker

Use the pinned server and a private configuration such as [nats-server.example.conf](config/nats-server.example.conf). Bind the broker only to loopback. Give only the internal HAB service its dedicated broker credentials. Products continue to use the authenticated HAB endpoint.

Set File storage, replicas one, and `sync_interval: always`. Audit the actual broker configuration before deployment. Do not infer fsync policy from the client version or stream INFO. Avoid `persist_mode=async`.

Keep server, account, stream, outbox, sender, recipient, and retained-record budgets finite. Reserve disk space for transactions, compaction, logs, and snapshots. Choose numbers from the actual workload and recovery requirements. This work does not measure a production sizing target.

Keep cache bounds finite and large enough to cover the admitted mailbox. Synchronous HAB prefetch reads verified stream messages directly.

## Observe failures

Read the owner-private `jetstream-health.local.json` for the last ready or degraded transition and a fixed reason code. The file is not a heartbeat. Monitor process liveness, disk availability, oldest pending admission, pending cleanup, quarantine, and broker storage errors separately.

When the broker is unavailable, already admitted bodies remain in the bounded outbox. The running host can return their pending receipt. Reconnection uses the same IDs. No request falls back to SQLite under another ID.

If the volume is unavailable, the host does not write health data into a fallback path. Inspect the mount and marker before restarting. Do not create empty replacement stores to clear an error.

## Back up and restore

Stop new admissions and quiesce the relevant services before taking a consistent backup. Include the broker stream snapshot, admission and ACK journal, Registry, Task Store, binding configuration, and recipient checkpoints. Keep credentials under a separate secret-management policy.

Store encrypted backups outside the source volume. Restore into an isolated directory or host. Update the expected device only after verifying the restored volume. Compare accepted IDs, body digests, saved receipts, engine request keys, and Task results before routing traffic.

The independent restore exercise is not implemented by this P5/P6 package. A broker snapshot alone is insufficient to restore the whole HAB state.

## Roll back

There is no SQLite delivery fallback. A code-only rollback keeps the same journal and broker store, so it works only to a build that opens the schemas this release wrote. This release writes delivery journal schema 4 and agent SDK inbox schema 4. Builds before the JetStream-only release (`3e203d7` and earlier) open journal schemas 1 to 3 only. They refuse a schema 4 journal with `journal_key_or_version_mismatch`, with or without `migrate_journal`, and there is no downgrade migration. Never rewrite a schema version to make an older build start.

Rolling back past a schema change means restoring the consistent backup taken while stopped, immediately before the upgrade started with `migrate_journal: true`. Prefer a forward fix. If a rollback is still required, reconcile by original ID every message whose outcome the restore erases. That is each message the new release accepted, and each message still `staging`, `pending`, `leased` or `quarantined` in the backup, because the new release may have delivered it after the backup was taken. Such an ID stays on the list even after the upgraded journal's purge deleted its row. Also reconcile every body that a restored recipient inbox holds unreleased, and every unreleased body retained only in the upgraded inbox copy. Its row may be `acked` in the backup, but an ACK proves only the save. The upgraded recipient may have executed that body after the backup, and the restored inbox would hand it to the application again.

A journal state never proves that a recipient did not save or execute a message. A recipient can save a body durably while its ACK never commits at the relay, and the row then ends `expired` or `quarantined`. Only `acked` is conclusive, and it proves only the save. The recipient's own records decide the rest.

1. Stop new admissions and drain. Keep recipients polling until no row is `staging`, `pending` or `leased`. Every row ends `acked`, `expired` or `quarantined` within one hour of its acceptance.
2. Stop the host and every recipient whose state is in the backup. Copy aside the schema 4 journal and all post-upgrade state the restore will replace: each recipient inbox, the Task Store, execution records and the host's `a2a-*.sqlite` files. These copies are the only record of what happened after the backup. From each recipient's copied execution records, export the sender and message IDs its application has handled as `{"recipient_id": "<agent ID>", "handled": [{"sender_id": "…", "message_id": "…"}]}`. The agent SDK inbox requires the application to save each body under that key before `releaseBody`, so the records hold it.
3. Build the reconciliation list from the copies. From the repository root, run `node scripts/relay-rollback-reconcile.mjs --upgraded-journal <schema 4 copy> --backup-journal <journal from the backup> --inbox <inbox copy>`, repeating `--inbox` for every agent SDK inbox copy, the host's `a2a-inbox.sqlite` included. Add `--backup-inbox <inbox from the backup>` for every recipient inbox the restore puts back, and `--execution-record <export>` for every recipient's export. The list combines both journals with retained inbox and execution-record IDs. An ID incomplete in the backup, or absent from the backup but retained only in recipient evidence after upgraded journal collection, is listed with `final_state: null`. For execution-only evidence the expiry is unknown (`expires_at: null`); its delivery action stays `unknown`, and `execution_record: handled` identifies the separate application evidence. IDs absent from every supplied source cannot be enumerated; obtain independent sender/application records before calling reconciliation complete. For each listed sender and message ID it prints the state in the backup, the final state, whether the recipient's inbox copy holds a record, and one action: `delivered`, `not_saved` or `unknown`. Under `restored_bodies` it lists each body a backup inbox holds unreleased, whether the upgraded inbox copy shows it `released`, `unreleased` or `absent`, whether the execution record lists it as `handled`, and one action: `do_not_process`, `process` or `unknown`. Under `retained_bodies` it lists unreleased bodies in upgraded copies that are not unreleased in the backup inbox, with `backup_record`, `execution_record`, and an action of `do_not_process`, `review_application_handoff` or `unknown`. Missing backup inbox evidence is not treated as an empty inbox. It also prints `restored_incomplete_expire_by`, the latest expiry among the IDs still incomplete in the backup. It only reads.
4. Restore every part of that one backup generation together. That is the broker stream snapshot, the journal, the Registry, the Task Store, the binding configuration and the recipient checkpoints. Never restore the journal alone or the broker store alone. A journal older than its stream rewinds receipts and ACKs, so the old build would deliver ACKed messages again and recipients could execute them twice.
5. Keep the earlier build stopped, with no listener open, until the backup time plus one hour plus the largest configured `max_clock_skew_ms` has passed, and at least until `restored_incomplete_expire_by`. Every ID in the restored state was first sent before the backup, so by then each one has expired. The earlier build then marks its journal rows `expired` instead of delivering them, a restored sender outbox marks its expired intents `expired_unknown` and the journal refuses them, and a restored inbox refuses an unseen expired delivery. An ID that a recipient saved or executed after the backup therefore cannot reach the restored recipient again through the relay, although that recipient lost its record of it. A rollback that starts more than an hour after the backup has already waited long enough. The wait does not cover a body already saved in a restored inbox: the inbox hands out a saved body regardless of its expiry. Step 6 settles those.
6. Before restarting each restored recipient, settle its `restored_bodies` against the copied execution records.
   - `do_not_process`: the upgraded recipient's application handled it after the backup. Record that result in the restored application store under the same sender and message ID, then release the body in the restored inbox with `releaseBody`, without handing it to the application.
   - `process`: no copy shows it handed off after the backup. The restored recipient may process it as usual.
   - `unknown`: the inbox copy released it with no execution record, or a copy is missing. Keep that recipient stopped until its operator decides from its own records. Never let it process the body to find out.
   Settle `retained_bodies` too. The full restore removes these post-backup saves from the active inbox; draining and the expiry wait do not transfer them. A `delivered` message is not proof that its application handoff finished.
   - `do_not_process`: recover the existing application record/result under the original sender/message key; do not execute it again.
   - `review_application_handoff`: the retained inbox has an unreleased body, the backup inbox has no row, and the supplied execution export has no handled record. Review the recipient's full Task/execution state for in-flight, failed or uncertain effects before authorizing continuation. If it proves no prior handoff, use an application-specific local recovery procedure to durably hand off the saved body from a working copy, using a compatible SDK and the original sender/message key. Preserve deduplication and any existing Task/run identity. Record the result in the restored application store before releasing the working-copy body. This is recovery of an already-saved body, not network delivery: do not resubmit it, inject it through `inbox.save`, change its ID, extend its expiry or downgrade a schema. Keep the immutable evidence copy. There is no generic recovery executor in this script; if the application has no safe recovery procedure, retain the body and keep that recipient stopped.
   - `unknown`: a backup or execution copy is missing, or the backup already released this body. Reconcile the conflicting/missing application evidence first. Absence from an export alone never proves that external effects did not start.
7. Start the earlier build with admissions still stopped. Settle every listed ID before routing traffic.
   - `delivered`: the recipient saved it, whether or not its ACK committed. Do not resend it. The restored sender's status lookup reports `expired` or `not_found`, so tell the sender from the list. Whether the recipient executed it, and with what result, is in that recipient's Task results and execution records in the copies, not in the restored Task Store.
   - `not_saved`: the recipient's inbox copy has no record of it, so its agent SDK never handed it off. Tell its sender it was not delivered. A new attempt is a new request under a new ID that the sender decides on. It is not an automatic replay.
   - `unknown`: there is no inbox copy for that recipient, or the record could already have been collected. Ask that recipient's operator to check its inbox, Task results and execution records by the original sender and message ID. Until then, tell the sender the outcome is unknown and do not retry.
8. A2A Tasks created after the backup are not in the restored state, and builds without host wiring ignore the `a2a-*.sqlite` files. Tell those Tasks' callers, using the Task results in the copied `a2a-tasks.sqlite`.

Do not delete the copies until reconciliation is complete. Do not replay uncertain work under new IDs, or claim Task completion from a broker ACK.

The root test `test/relay-rollback-reconcile.test.js` runs the listing on a real JetStream journal and agent SDK inboxes. It covers an ID staged before the backup and saved after it with its ACK lost, an ACK lost after a save, an acked ID, an unsaved ID and a recipient without an inbox copy. A second drill covers a body acked and saved before the backup and executed after it, a body acked before the backup and still unprocessed, and an ID pending at backup whose row the upgraded journal purged. It marks unfinished rows `expired`, and deletes the purged row, in place of waiting out the drain and the retention. A third drill runs the relay on its own broker and follows steps 1 to 7 with real files. It backs up the journal, the JetStream store dir, the recipient inbox and its application store together while delivery is stopped. After the backup the current build delivers an ID pending at backup and a new ID, and the recipient executes them and a body saved before the backup. The drill copies the upgraded state, restores every part of the backup, runs the listing on the copies, settles the `do_not_process` body in the restored application store, holds the relay stopped until `restored_incomplete_expire_by`, and restarts the relay and the recipient on the restored state. The broker then runs on the backup's stream, the relay delivers nothing again and the restored recipient executes the `process` body. The drill additionally leaves a new ACKed body unprocessed after the backup and recovers it locally from a working copy with its original key while the relay is stopped. Both unprocessed bodies run once and nothing runs twice. Its messages expire 20 seconds after the backup, so the hold is a real wait. It restarts the current build on the restored state, not the earlier build.

The independent `test/relay-rollback-reconcile-unit.test.js` uses minimal SQLite projections to cover post-backup journal-GCed IDs retained in inbox or application evidence, missing copies, and handled/unhandled retained bodies. A 150,000-incomplete-row backup exercises the CLI entry point without printing its large list, checks the latest incomplete expiry without exceeding the runtime's argument-count limit, preserves unknown outcomes and verifies both journal files remain unchanged. It proves read-only list behavior, not actual timed journal collection, production sizing or production application recovery.

## Interpret platform evidence

The code uses Node, SQLite, filesystem operations, and the official NATS client. The installer pins Linux amd64 and arm64 artifacts. A Linux container proof establishes execution in that container's kernel and filesystem environment. It does not establish a selected VPS provider's volume durability or availability.

One VPS and one volume form one failure domain. Three broker processes on that VPS do not provide independent host or storage failure domains. OS power faults, actual SSD disconnection, full disks, and corruption injection require a separate isolated fault model. None is performed against a live host by this package.
