# Fixed pilot compatibility

This page records the earlier fixed-connectivity prototype and its local trial history. It is not acceptance of the current inventory profile, new key lifecycle or no-site dependency bundle. Current inventory preparation and remaining gates are in [MVP acceptance](mvp-acceptance.md) and [HAB roles](hab-roles.md).

`HermesRuns.connectPilot` supports the constrained Runs wrapper without opening extra API routes or accepting model/session/tool overrides. It submits exactly `{"input":"Reply with exactly HUB_HERMES_OK."}`. It checks authenticated `pilot_policy` (that exact input, tools zero, session overrides false, personal context false), required Bearer auth, submission/status and durable idempotency. It does not request `/v1/toolsets` in this mode, and never interprets 404 as tools zero. Standard mode still requires toolsets and its original fixed contract.

Completion requires exact `HUB_HERMES_OK` with actual runtime `openai-codex` / `gpt-6.1-sol`. Only then is the result normalized to the Hub's existing connectivity success text. Newline/extra output, model/provider mismatch and uncertain terminal status keep the execution slot/receipt for reconciliation.

The contract is `hermes-hub-fixed-pilot-v1`, distinct from standard mode. Original deadline/retention/contract and runtime scope remain persisted. Old/missing/foreign contracts are not migrated or blindly resubmitted. Lost admission acknowledgement is reconciled only with the same verified namespace, exact payload and original unextended deadline. Receipt reopen and known-ID polling are tested against a temporary mock API.

## Read-only independent inspector

`PilotInspector` checks local files/process independently of API-reported booleans. An operator must supply a private, independently reviewed policy; no policy generator, real profile defaults, secret reader, launcher, daemon or live worker entry point is installed. Supplying hashes of arbitrary code is not a safety review.

Required policy binds the approved loopback endpoint, dedicated profile, reviewed wrapper/config hashes, exact source commit, interpreter digest, complete executable/import dependency trees, credential metadata identity and durable idempotency DB identity. The derived scope hashes this policy so replacement of code, credentials, database namespace or configuration cannot silently reuse old receipts. Credential contents are never opened: only ownership, private permissions, device/inode/size/mtime/ctime are compared. PID files and nonsecret reviewed code/config are read. No shell command or destination comes from tasks.

The default macOS observer uses fixed bounded `ps`, `lsof` and read-only git commands to confirm PID/UID/start time/exact command, only the approved loopback listener, source commit. It avoids `git status` and disables fsmonitor for the metadata read, so local git status filters/monitors cannot become execution probes; the complete code-tree digest is the authoritative content check. It does not inspect process environment values. Two observations and file scans must agree. All regular files in approved code trees (including ignored code, bytecode and arbitrary archive names) are hashed; every file and directory must predate the process's earliest start second. Default snapshot trees reject owner/group/other-writable code files or directories and symlinks. Private/runtime data and unexpected changes reject evidence; explicitly reviewed system runtime and package-data handling are described below. Git metadata is excluded and must not be importable. Inspection returns null on any rejection; no warning-only fallback exists.

The policy review must cover **all Python import roots, interpreter/standard library/site-packages, `.pth`/archive/custom loader behavior and a sanitized trusted launch environment**. Undeclared import roots or an uncontrolled launch environment invalidate the prerequisite: this inspector does not independently discover `sys.path` or read secret-bearing environment values. Use an approved immutable executable snapshot and prevent bytecode/cache/code mutation after startup. The existing pilot's mutable checkout/venv may fail these strict checks; mock success does not establish its real policy. Pins must not be automatically refreshed after mismatch. An operator must review and approve any new namespace/policy and reconcile old receipts.

Evidence expires within 30 seconds. API policy corroborates the independent approved-code/process gate; it does not replace it. `ProcessProbe` injection is only a trusted testing seam. Production must use the built-in observer, not a fabricated observation. Dummy policies and mock API tests alone do not establish the real runtime boundary.

A subsequent read-only metadata check confirmed that the existing installed runtime does **not** satisfy this inspector: its checkout is owner-writable, its venv interpreter is a symlink, and its dependency tree exceeds the current 512 MiB per-tree limit. Its editable import hook points back to the mutable checkout. The dedicated API was stopped. A complete approved runtime snapshot and bounded compatibility review are still required before a live Hub roundtrip; copying the venv alone is insufficient. Existing Desktop files, authentication and configuration have not been changed.

## Bounded snapshot compatibility and preflight status

The tree limit remains 512 MiB by default. An explicitly reviewed tree may declare `maxBytes` up to 1 GiB; the policy permits at most six roots and at most 2 GiB of declared scan budgets in total. The 100,000 entries per tree and 64 MiB per file limits remain. All trees now reject effective-user write access, including ACL grants. Snapshot source/venv trees still additionally reject write permission bits and every symlink.

An explicit `systemRuntime` tree requires every entry to be root-owned and non-writable by the effective user; it retains content hashes and startup ctime checks. Only explicitly pinned system symlink aliases are allowed, and their canonical targets must lie in another measured system root or the same measured system root. Unknown aliases and changed targets reject. OS libraries supplied by the trusted macOS installation are a separate launcher-review prerequisite, not an implicit allowance for arbitrary native libraries.

`reviewedResources` can identify at most eight exact relative package-data directories named `logs`, `runtime` or `secrets`. This only resolves a name collision such as an SDK's public API-schema directory; every byte and entry is still measured and permission checked. It must never identify actual private or runtime data. `.env` files remain rejected and cannot be exempted. A system `lib` root may explicitly exclude only the exact `python3.<version>/site-packages` directory. This is valid only when the reviewed launcher disables that root at runtime: future imports, reads and native loads must reject it before execution, and already-loaded modules/native images must be checked. Symlink aliases cannot reintroduce it. `scripts/python_import_guard.py` supplies the import/read/ctypes guard for a reviewed fixed wrapper; it is not a general Python sandbox or a substitute for review of the launcher, native dependency graph and `.pth` startup behavior.

During the authorized local preparation, a private code-only snapshot was created without copying credentials or execution history. Its editable hook was removed, and the isolated import preflight checked the actual fixed wrapper with user-site and bytecode writes disabled. It imported 1,308 modules without starting the API or creating an agent. The native loader also uses the macOS Python launcher executable, so measuring only the Python binary and standard-library directory is insufficient.

The initial full Framework scan failed the bounded gate. After separate operator approval, a five-root manifest measures the code-only snapshot, copied venv, system standard library, Python core and native launcher, with disabled global packages excluded under the runtime guard. The installed mutable checkout remains outside the import boundary. The copied launcher checks both `sys.prefix` and `sys.base_prefix`; `processInterpreterPath`, when specified, must equal a separately measured `systemRuntime` file root and is used for exact process-command matching. No broad command prefix is accepted. Production entry points still default to 401.

The isolated wrapper import preflight passed without API or agent creation. All five roots passed nonsecret hash/ownership/effective-write checks. Runtime files, credentials, process logs and real identifiers remain local and uncommitted. The separately authorized one-task local trial completed through the official HTTP MCP client: Hub submit → constrained Hermes Runs → MCP get returned `succeeded` and the normalized fixed result. Repeated get returned the same result; exactly one model-admission POST occurred, the receipt cleared, and one terminal outbox record remained durable. The trial Hub and dedicated API were stopped, the dedicated port closed and its PID file removed. No new credential or persistent launcher was installed. This establishes the fixed local route only; Dots/Grok authentication, hosted identity/egress and event delivery are not validated.

## Connection approval boundaries

1. Approve reviewing/building the complete immutable code/runtime snapshot and sanitized manual launch contract, then populate a local-only pinned policy from nonsecret reviewed files and credential/store metadata. Do not issue or rotate authentication automatically.
2. Approve manual start of the dedicated loopback API, runtime-only reading of its existing API key by the Mac adapter, and local capabilities/status calls. No Desktop fallback, cloud transmission, daemon or public endpoint.
3. Approve one fixed Hub task/new independent model run with the exact pilot payload. Keep concurrency one, journal original replay contract/deadline, poll only its ID, retrieve the result explicitly with authenticated MCP get, and manually stop/confirm shutdown.
4. Approve a concrete local Hub requester/worker authentication mapping or a separately verified private hosted boundary. Production Node/Worker entry points still default to 401; a fixture verifier is not a production identity scheme.

The source does not install a live launcher, credentials, a daemon or a production verifier. Local trial authorization does not authorize cloud deployment, new credentials, personal input or automatic continuation. Events/Dots automatic continuation remains separate.
