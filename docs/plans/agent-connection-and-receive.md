# エージェントの接続と導入を簡単にする

実装計画。基準となる HAB の `main` は `235c30c`（2026-11-21）。

## ねらい

新しいエージェントを 1 つつなぐ手間を減らす。今の[設定手順書](../connections/agent-setup.md)では、共通の準備が 6 段、製品ごとの受け方の設定が 1〜4 段あり、Auth0・HAB の host（Mac mini）・製品の画面の 3 か所を行き来する。2026-11-14〜21 に Dots・Muse・Grok・claude.ai・Hermes をつないだときに時間を取ったのは、次の 4 つだった。

1. 接続の登録：Auth0 のログで主体（subject）を探し、OAuth v2 の接続台帳を手で書き、`hab:admin connect` を打つ。名前と ID を何度も照合した。
2. 起こし方の設定：製品ごとに違う（Dots はイベントタスクの文、Grok は routine の URL と鍵を host 設定に書いて再起動、Muse は予定タスク、Hermes は notifier とプラグイン）。
3. 呼び鈴を足すたびの host の再起動：運用者の呼び鈴（ADR-029）が host の設定ファイルにある。
4. 動いているかの確認：呼び鈴が鳴ったか、読まれたか、返事が来たかを、監査記録と DB を突き合わせて調べた。

製品の画面での操作（MCP の追加と OAuth のログイン）は HAB から自動化できない。HAB 側でできるのは、それ以外を減らすことと、迷わない案内を出すことである。導入の完了は、利用者が選んだアプリの会話で最初の 1 通を確認できた時点とする。

## 方針（本人の判断、2026-11-21）

- 課題は「各エージェントとの接続と導入の難しさ」。Hermes だけに効く 1 コマンドのセットアップより、全製品に効く仕組みを先にする。
- doctor（診断）は必ず入れる。
- 登録は「承認待ちに記録して、運用者が承認する」方式にする（招待コードは使わない）。HAB に登録できるのは本人が承認したエージェントだけ、という決まりは変えない。

## 段の順番

| 段 | 内容 | 減る手間 |
| --- | --- | --- |
| 1 | doctor | 4（どこで止まっているかを 1 コマンドで出す） |
| 2 | 承認待ちからの登録 | 1（Auth0 のログ探し、台帳の手書き） |
| 3 | 呼び鈴を台帳に移す | 3（host の再起動） |
| 4 | ping と製品レシピ、onboard | 2 と 4（試験の 1 通で合否を出し、製品ごとの手順を 1 か所から出す） |

各段は独立した PR にし、前の段がマージされてから次に進む。8 PR 計画との関係は付録 A に置く。

## 1. どこで止まっているかを診断で出す（doctor）

運用者が `doctor` で宛先を指定する。CLI は `scripts/hab-admin.ts`、台帳と受信状態の読み取りは `src/host/admin.ts` に置き、`hostAdminStatus` と同じ開き方と算出を使う（管理 CLI は移行が要る DB を先に `registry_upgrade_pending` で断るので、診断のための別の開き方は要らない。開いたときの移行処理が何も書かないことをテストで確かめる）。`--address` を付けないときは、全アドレスを 1 行ずつ出す。

```sh
npm run hab:admin -- --config <host-config> doctor [--address <address>]
```

最初の版では、製品で実行した `hab_discover` の結果を運用者が渡す入力（`--whoami-file`）は作らない。手作業が 1 つ増えるうえ、4 章の `ping` で実際の 1 通を確かめるほうが確実だからである。名義の項目は、台帳から分かる範囲（接続・グループ・権限）で出す。

| 表示項目 | 判定に使う情報 |
| --- | --- |
| アドレスと接続の紐づけ | 台帳の不変 ID、登録状態、紐づけと必要な権限、接続の承認期限（`approved_until`）。 |
| 名義 | 接続が結び付くグループと、その中でこのアドレスを選べるか。製品側でどの名義を選んでいるかは分からないので、それは `ping` で確かめる。 |
| 対象の会話 | 台帳上の会話名（`hab:admin session`）と、仮の名前か運用者が付けた名前か。製品が会話を証明する仕組みはまだないので、実際にその会話が動いているかは `unknown` とし、照合の仕組みは作らない。 |
| 受信方法と動作 | 台帳の `hook`、`poll`、`on_request` と、`status` が観測した呼び鈴の結果や最終既読、`poll_overdue`、`recipient_absent`（と `recipient_absent_since`、PR-7）、呼び鈴の `live`／`lapsed`。`hook` の宛先は、呼び鈴（購読か運用者の登録）があること、最後に鳴らした結果、その後に読まれたかを分けて出す。運用者の呼び鈴が `127.0.0.1` を指す場合は、その製品の notifier の `wake` の待ち受けと鍵が設定されているかを `next_action` で確認させる（診断はホストの外のファイルを読まない）。 |

応答は `address` と `checks` を持つ JSON とする。 `checks` は `registration`、`identity`、`session`、`receive` の4項目（2 章の承認待ちがあれば `registration` に含める）。各項目は `state`、固定の `reason`、確認に使った公開可能な値 `evidence`、次の操作 `next_action` を持つ。 `state` は `ok`、`problem`、`unknown` のいずれか。コマンド自体が成立したら、各項目の結果を出して終了コード0を返す。登録されていないアドレスと DB を読めない場合は管理 CLI のエラー処理に従う。診断には認証情報やメッセージ本文を含まない項目だけを写す。

たとえば呼び鈴が HTTP 2xx で受理され、最終既読が更新されていなければ、受理時刻と最終既読を別々に出す。次の操作として対象製品の実行履歴を確認するよう表示する。会話が観測できない状態は `unknown` とし、宛先の受付可否は台帳の登録状態に従う。

### 診断の受入条件

- [ ] `test/host-admin.test.js` で、登録されていないアドレス、接続の承認期限切れ、呼び鈴なし、呼び鈴の受理と未読の併存、`poll_overdue`、`recipient_absent`、全アドレスの一覧を検証する。
- [ ] `doctor` の実行前後で、宛先の登録状態、接続、既読、通知回数が一致する。
- [ ] 実際の会話への到達は 4 章の `ping` で別に記録する。CLI の診断だけで実機の到達を合格にしない。

## 2. 承認待ちからの登録

### 今の動き

`src/host/oauth-auth.ts` の検証は、issuer・audience・scope を確かめたあと、署名を確かめる前に、主体と client の組を接続台帳（OAuth v2 の private 設定 `connections`）から探す。見つからなければ `client_not_registered` か `subject_not_registered` で断り、監査には理由だけを残す。そのため運用者は、Auth0 の管理画面のログで主体を探し、台帳に手で書き足し、`hab:admin connect` を打つ必要がある。

### 変えること

1. 検証の順番を入れ替え、署名の検証を台帳の照合より先にする。台帳にない組は、署名・issuer・audience・scope・期限がすべて正しいときだけ「承認待ち」に記録してから、今までどおり断る。偽の token で一覧が埋まらないようにするためである。
2. 承認待ちは host の状態ディレクトリの SQLite に置く。1 行は `pending_id`、`issuer`、`subject`、`client_id`、`first_seen_at`、`last_seen_at`、`attempts` だけで、token・scope の中身・本文は残さない。同じ組は 1 行にまとめ、上限は 32 行、14 日来なければ消す。上限に達したときは、接続台帳にまだ主体がない組の中から `last_seen_at` の古いものを消して入れる。台帳に主体がある組（本人の別製品や、DCR でつなぎ直した製品）の行は、主体のない組のために消さない。知らない相手の行で本人の行が締め出されないようにするためである。
3. `hab:admin pending` で一覧を出す。主体は先頭と末尾だけを見せ、client ID はそのまま見せる（Auth0 の画面で、どの製品のアプリかを照合できる）。
4. `hab:admin approve --pending <pending_id> --address <bot@agent.hab> [--days 365]` で、次を 1 回で行う。
   - 接続台帳に `subject`・`client_id`・新しい `connection_id`・`approved_at`・`approved_until`・`state: active` の行を足す。台帳ファイルは一時ファイルから置き換え、書く前にバックアップを取る。
   - 今の `hostAdminConnect` と同じ手順で、アドレスを登録して接続に結び付ける。
   - アドレスがすでに別の接続に結び付いていれば、そのアドレスに今許している操作をそのまま引き継ぐ。既定の 5 操作に戻さない。DCR では claude.ai や Grok がつなぎ直すたびに新しい client ID になるので、つなぎ直しのたびに許可が広がったり狭まったりしないようにする。
   - 同じ `subject` と `client_id` の行がすでに台帳にあれば、行を足さずにその行を使い、結び付けの手順から続ける。同じ組の行が 2 つあると `parseOAuthConfig` が設定全体を断り、入口全体が止まるためである。途中で止まった `approve` をもう一度打っても、結果は 1 回打ったときと同じになる。
   - 承認待ちの行を消す。
   台帳は要求ごとに読み直されるので、承認後に host の再起動は要らない。ただし今の検証は、承認より前に発行された token を `token_before_approval` で断る。そのためエージェントは、承認後に発行された token で通る。製品の更新（access token は最長 600 秒）を待つか、製品の画面でつなぎ直す。`approve` はそのことを次の操作として表示する。承認の開始時刻を前にずらして古い token を通すことはしない。
5. `hab:admin reject --pending <pending_id>` で行を消す。断った組がまた来れば、また承認待ちに入る。
6. 接続を外す操作は、`hab:admin revoke --connection <connection_id>` として別に設ける（DCR の計画、PR #263）。`approve` は承認待ちの行を、`revoke` は台帳の接続を指すので、名前も引数もぶつからない。

承認は今までどおり運用者の操作であり、エージェントが自分で通ることはない。`approve` は Mac mini の安全確認の対象（本人の言葉が要る操作）のままである。

### 受入条件

- [ ] 署名の正しい未登録の組だけが承認待ちに入り、署名の違う token・期限切れ・scope 不足は入らない。
- [ ] `approve` のあと、承認後に発行された token で `hab_status` が通る。承認前の token は今までどおり `token_before_approval` で断る。再起動なし。
- [ ] 台帳の書き換えが途中で止まっても、前の台帳か新しい台帳のどちらかが残る。
- [ ] すでに接続のあるアドレスに `approve` しても、許している操作が変わらない。
- [ ] 同じ組に `approve` を 2 回打っても、台帳の行は 1 つで、`parseOAuthConfig` が通る。
- [ ] 承認待ちが 32 行で埋まっていても、台帳に主体がある組は承認待ちに入る。
- [ ] 承認待ちの記録に token と本文がない。`hab:admin status` に承認待ちの件数が出る。
- [ ] 実機：新しい製品を 1 つ、Auth0 のログを見ずに `pending` → `approve` でつなぐ。

## 3. 呼び鈴を台帳に移す

運用者の呼び鈴（ADR-029、`ingress.events.doorbells`）は host の設定にあり、起動時に `configureStatic` で読む。足すたび・変えるたびに host の再起動が要る。

- `hab:admin doorbell add --address <a> --url <url> --secret-file <path>`、`doorbell remove --address <a>`、`doorbell list` を足す。URL の規則（公開 HTTPS、または同じ Mac の notifier 用の `127.0.0.1`／`[::1]`、ADR-032）と鍵ファイルの規則は今と同じ。
- 登録は `events.sqlite` に置き、動いている host が次の配送の確認で読み直す。再起動は要らない。
- 設定ファイルの `doorbells` は当面そのまま読む（今の Mac mini の設定で起動できる）。同じアドレスが両方にあれば台帳を優先し、`ready` の行で 1 回知らせる。
- 呼び鈴を新しく登録したら、PR-7 の「相手がいない」の印を解く（`configureStatic` と同じ規則）。

受入条件：再起動なしで登録・削除が効く。設定ファイルだけの古い構成でも起動できる。鍵の中身が出力や記録に出ない。

## 4. 製品レシピと onboard

製品ごとの違いを、コードの分岐ではなくデータ（レシピ）で持つ。レシピは `config/products/<製品>.json` に置き、公開してよい内容だけを書く。

| 項目 | 例 |
| --- | --- |
| 受け方 | `hook`（MCP イベント／運用者の呼び鈴）、`poll`（間隔）、`on_request` |
| 製品の画面での手順 | MCP の追加先、Auth0 のアプリの種類と callback、つなぎ直しが要る場面 |
| AI に渡す文 | 手順書の「渡す文」と同じもの（見張りの頼み方、許可する相手） |
| 運用者の設定 | 呼び鈴の要否、`receive` の値 |
| 確かめる項目 | doctor で `ok` にすべき項目と、試験の 1 通で見る段（呼び鈴・既読・返信） |

`hab:admin onboard --address <a> --product <製品>` は次を順に行い、どこまで済んだかを毎回同じ形で出す。

1. そのアドレスに承認済みの接続がすでにあれば、2 を飛ばして 3 へ進む（`approve` のあとに再実行した場合）。
2. なければ承認待ちを探す。承認待ちもなければ「製品の画面で MCP を追加してログインする」手順を出して止まる。あれば承認の案を見せる（実行は運用者の `approve`）。
3. レシピの `receive` と、要るなら呼び鈴を設定する。
4. レシピの「AI に渡す文」を、アドレスを埋めて出す。
5. `ping` で試験の 1 通を送り、呼び鈴・既読・返信の時刻と、止まった段を出す。

`hab:admin ping --address <a> [--wait <秒>]` は単独でも使える。送信元は試験専用のアドレス（例 `ping@hab.hab`）を host に 1 つだけ作り、既存のエージェントのアドレスは使わない（受け手に本物のメッセージに見えないように）。本文は固定の短い試験文にし、`kind` は `notice` にする。返信は求めるが、来なくても失敗にはしない（「返信なし」と出す）。

[設定手順書](../connections/agent-setup.md)は、レシピから作る形に寄せていく（最初の PR では手で合わせる）。

4 章は `ping` を先に出し、レシピと `onboard` はそのあとにする。1〜3 章と `ping`、doctor の「次の操作」、手順書で十分に迷わなくなったと分かれば、`onboard` は作らずに止める。

受入条件：Dots・Grok・Muse・Hermes・claude.ai の 5 製品のレシピがある。`onboard` を途中で止めて再実行しても、済んだ段を繰り返さない。`ping` の結果が doctor の表示と食い違わない。

## 5. 今回は入れないもの（条件がそろったら）

- **Hermes Desktop の 1 コマンドのセットアップ**（旧計画の 2 章）：Hermes を 2 台目に入れる、またはプロファイルを作り直すときに、4 章のレシピの Hermes 版として作る。対象はプラグイン方式（`config.json`）・notifier の `wake`・呼び鈴で、古い reader 方式は対象にしない。
- **製品が示した会話への引き渡し（Codex など）**（旧計画の 3 章）：Codex は 2026-11-20 の確認で、アプリ内の app-server が stdio だけで外から入れなかった。`codex app-server daemon start` の常駐がアプリの会話と同じものに見えるか、nenwa の `codex queue --thread` で入れるかを実機で確かめてから決める。
- **製品側の `session_gone`**：PR-7 の受け口に、製品（Hermes の notifier など）が 410 と `session_gone` を返す部分。
- **Auth0 のアプリを製品ごとに手で作る手間**：減らすには DCR（動的クライアント登録）を許すかどうかの判断が要る。認証の方針の変更なので別に扱う。
