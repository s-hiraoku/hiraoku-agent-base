# HAB ダッシュボードからエージェントをつなぐ

運用者は既存の登録一覧から「エージェントをつなぐ」を開き、製品での接続、HAB での承認、受け取り方の設定、試験の順に進む。各画面には今分かっていることと、次にする操作を一つ出す。導入の完了は、運用者が対象製品の会話で試験メッセージを確認した時点とする。

導入計画の第5段を具体化する。#278 で登録一覧、診断、接続案内を実装した。試験送信は CLI と画面で同じ `ping` の処理を使う。申請の承認・受け取り方・呼び鈴の設定は、順に画面から既存の管理処理へつなぐ。 [導入計画 第5段](agent-connection-and-receive.md#5-ダッシュボードから見る操作する)

## 同じリポジトリに組み込む

現行の HAB 管理画面で、アドレスを検索し、登録状態で絞り込み、宛先をコピーできる。一覧から診断を開き、製品の設定手順へ進める。 [GUI の製品仕様](../hab-product-spec.md#5-gui仕様)

画面と HTTP の入口は HAB 本体の `src/admin/` にあり、現行の SQLite 版 host の状態を管理関数で読む。閲覧画面は `npm run hab:dashboard -- --config /path/to/host-config.json` で起動し、表示されたランチャーファイルをブラウザで開く。画面と読み取り API は MCP と独立したプロセスの同じループバック origin で提供する。追加する変更操作も、CLI と画面で検証・状態判定・台帳更新の処理を共有する。 [SQLite への移行判断](../hab-decisions.md)

## 登録一覧から始める

```text
登録一覧                                     [エージェントをつなぐ]
検索 [                       ]    登録状態 [すべて]

アドレス            登録        受け取り方     受信箱      会話
helper@demo.hab     承認済み    手動            未読なし    未確認
                    次にすること  [試験メッセージを送る]
```

登録一覧には `hostAdminDoctor` が返す `registration`、`receive`、`reading`、`session` と最初の問題を表示する。行を開くと、それぞれの理由、観測時刻があればその時刻、次の操作が見える。アドレスの検索、絞り込み、コピーは一覧で行う。「エージェントをつなぐ」は製品選択から、新しくつなぎ直すときは該当アドレスの行から始める。 [診断の実装](../../src/host/doctor.ts)

| 段階 | 画面で行うこと | 次に進む条件 |
| --- | --- | --- |
| 製品で接続 | 製品を選び、MCP の接続先と製品レシピの手順を表示する。運用者は製品の画面でコネクタを追加してサインインする。製品で読み取り専用の `hab_discover(action=whoami)` を、利用できる場合に実行し、ダッシュボードに戻って最新の登録状態を取得する。 | 対象製品の `whoami` が意図したアドレスと不変 ID を返せば、本人が照合して受け取り方へ進む。承認を求められた場合は申請を確認する。 |
| 承認 | 運用者は申請を選び、新規の HAB アドレスを入力する。つなぎ直しでは一覧で選んだアドレスを使う。申請、アドレス、承認期限を確認して承認する。 | 台帳への登録と紐づけが確定したら「承認済み」を表示する。製品で新しい token を取得し、`whoami` を再実行する手順を案内する。 |
| 受け取り方 | レシピに沿って受け取り方を確認し、必要な構成でだけ呼び鈴を設定する。対象アドレスを入れた「AI に渡す文」はコピーできる。 | `doctor` の受け取り方と次の操作を表示する。手動受信なら製品で受信箱を開く案内を出す。定期受信なら製品の予定を確認する案内を出す。 |
| 試験 | 対象アドレスと固定の試験文を確認して「試験メッセージを送る」を押す。`ping` が観測した受付、呼び鈴、受信箱の読み取り、返信を時刻付きで表示する。最後に対象製品で試験メッセージを確認する。 | 会話で確認できたら完了。返信は観測できたときに表示する。呼び鈴を使わない構成には製品で確認する手順を出す。 |

現行の画面では Dots、Grok Bot、Muse、Hermes Desktop、claude.ai を選び、設定手順書の該当箇所を開ける。レシピがそろったら、接続案内をそのデータから表示する。製品画面で実行する手順と、HAB 画面で確かめる項目を同じレシピから表示する。画面を開き直したときは host から状態を取り直し、既に承認済みの接続はその続きから進める。試験結果には試験メッセージの観測だけを使い、アドレス全体の最終受信箱読み取り時刻は診断欄に表示する。 [製品別の設定手順](../connections/agent-setup.md) · [レシピと試験の計画](agent-connection-and-receive.md)

## 申請とアドレスを確かめて承認する

承認待ちには、マスク済みの主体、client ID、最初と最後の時刻、回数を表示する。製品名を付けるのは、host が設定から client ID との対応を確かめられるとき。`doctor` の承認待ち表示は一覧への案内に使う。どの申請をどのアドレスに結ぶかは、運用者が申請を照合して選ぶ。申請が見当たらないときは、製品で再度 HAB を呼び出してから一覧を更新する。動的クライアント登録では、製品の認可リクエストにある client ID を申請と照合する。登録された callback URL の集合が対象製品の集合と完全に一致し、実際の redirect URI がその集合に含まれることを確認してから承認へ進む。 [DCR の照合手順](auth0-dcr.md#7-リスクと抑え方)

確認画面には新規登録かつなぎ直しかを明示する。サーバーが確認時の申請 ID と申請の世代、宛先、承認期限を操作に結び付ける。新規登録では宛先が空いていること、つなぎ直しでは宛先の不変 ID と Registry のアドレス・グループの状態および版を保持する。申請の世代は行を作るたびに変わり、同じ申請への再サインインでは維持する。

承認・却下は CLI と共通の処理を使う。承認は OAuth 台帳を書き換える前に、申請が有効で世代が合い、宛先が確認時の状態と一致することを、同時更新を防ぐ境界の内側で確認する。却下も対象の世代が一致する場合だけ申請を削除する。同じアドレスへの CLI 操作や却下後の再申請と競合したら、台帳・Registry・申請を変えず、確認画面に戻す。途中で中断した承認の再開では、最初に確定した対象と権限を使う。アドレスの既存権限の引き継ぎと、承認時刻以後に発行された token の条件は共通処理が適用する。 [承認待ちの登録計画](agent-connection-and-receive.md#2-承認待ちからの登録)

承認済みは台帳の状態を表す。対象製品で得た `whoami` のアドレスと不変 ID を運用者が照合するまで、製品の接続は「未確認」と表示する。名義の選択が必要なら、確認済みの宛先を `as_address`、不変 ID を `expected_agent_id` に指定する。ツールが使えない場合も、台帳だけを根拠に接続を確認済みとせず、実際の会話での試験を案内する。古い token を使用中なら製品側での更新を案内する。動的クライアント登録でつなぎ直しが新しい申請を作った場合は、該当する申請の確認に戻る。 [接続後の本人確認](../connections/claude-code-connection.md)

## 呼び鈴と試験は対象を確認して操作する

受け取り方は `receive` と同じ処理で設定する。呼び鈴一覧ではアドレス、設定元、ホスト名を見せる。追加では運用者が host 上で用意した登録元の名前を選ぶ。URL と鍵ファイルはサーバー側で解決して `doorbell add` に渡す。この方式なら、Webhook の URL と鍵をブラウザへ渡さずに登録できる。削除では対象を表示して確認する。設定ファイル由来の呼び鈴に戻る場合は、確定する前に表示する。 [呼び鈴の台帳化計画](agent-connection-and-receive.md)

試験は運用者が確定した操作ごとに一通送る。送信前に、操作 ID、運用者、試験専用の送信者 ID、宛先の不変 ID、メッセージ ID と確定した送信内容を host の永続記録に残す。CLI と画面は同じ `ping` の処理と記録を使い、同じ操作 ID と同じ送信内容で再送された要求は、元のメッセージ ID で配送層の重複防止を使う。内容や宛先の異なる要求は拒む。

画面を再表示したときやサーバー再起動後は、元の操作 ID から受付結果を照合する。確定した証拠が得られなければ「結果は未確認」と表示する。再試行は記録した送信内容と期限を使う。ページを開く、診断する、更新するだけなら読み取りに限る。 [配送の重複防止](../hab-messaging-spec.md#6-同一性時刻期限)

## 運用者の権限で操作する

現行のダッシュボードはループバックで待ち受ける。所有者だけが読める一時ランチャーのフォームを送信すると、閲覧または運用者のセッションが発行される。一度使った起動用の証明は交換し、セッションの鍵はブラウザのメモリに置く。セッションの有効期間は 15 分。 [閲覧サーバーの実装](../../src/admin/server.ts) · [画面の実装](../../src/admin/web/app.js)

管理操作を追加する段階では、閲覧用の鍵から管理権限を得られないことを先に確かめる。承認待ちの詳細と運用操作は、ローカルの運用者を別に確認して発行する有効期限付きの管理セッションに限定する。日常の送受信と試験送信は、起動時に選んだ運用者モードと、設定済み名義の MCP 権限を使う。閲覧用と管理用の資格情報は URL、履歴、ログ、ブラウザの永続ストレージに残さず、再起動や失効後は再認証を求める。HTTP の入口では Host を固定し、変更操作ごとに管理セッション、Origin、CSRF、確認時に結び付けた操作 ID と対象を検証する。

画面には固定の状態、理由、次の操作、許可した観測値を返す。HAB の認証 token、Webhook の鍵・URL、配送された本文は host 内に置く。監査には操作者、対象、操作、結果、時刻を残す。 [管理画面の公開範囲と監査](agent-connection-and-receive.md)

## 実装順と受入条件

| 第5段の実装順 | 確かめること |
| --- | --- |
| 登録一覧と製品の案内（#278 実装済み） | 既存の検索、絞り込み、コピーが使え、5 製品それぞれの設定手順を開ける。対象の `doctor` と画面の4項目が同じ状態を示す。未観測の会話は「未確認」と出る。 |
| 承認待ちと受け取り方 | 運用者が申請を承認・却下し、受け取り方と呼び鈴を画面で設定できる。CLI で見た結果と一致する。申請失効・却下後の再申請や、確認後の CLI による宛先変更では書き込みが発生せず、現在の情報で選び直す。二重操作や中断からの再開でも同じ対象と結果を保つ。 |
| 試験と完了 | 運用者が対象製品の会話で最初の一通を確認できる。手動受信と呼び鈴による受信で、受付、呼び鈴、読み取り、返信がそれぞれの証拠どおりに表示される。送信の直後に応答が失われ、再起動後に CLI または画面で同じ操作を照合しても一通のままになる。 |

結合試験では、同じ host の状態を CLI と画面で確認する。匿名、閲覧用の鍵、別オリジンでは、管理セッションを取得できず、変更要求も拒否されることを確かめる。ループバック外からの接続を拒否し、画面、応答、履歴、監査に保護対象の値が含まれないことを確認する。実機では、新規接続の運用者が Auth0 のログ調査や台帳の手編集をせず、対象の会話で一通目を確認できるかを確かめる。
