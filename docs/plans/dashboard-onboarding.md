# HAB ダッシュボードからエージェントをつなぐ

運用者は既存の登録一覧から「エージェントをつなぐ」を開き、製品での接続、HAB での承認、受け取り方の設定、試験の順に進む。各画面には今分かっていることと、次にする操作を一つ出す。導入の完了は、運用者が対象製品の会話で試験メッセージを確認した時点とする。

導入計画の第5段を具体化する設計。診断と承認待ちからの登録は `main` に反映済み。まず診断と接続案内を画面から使えるようにし、承認などの変更操作と試験送信は、それぞれが依存する管理処理につなぐ。 [導入計画 第5段](agent-connection-and-receive.md#5-ダッシュボードから見る操作する)

## 同じリポジトリに組み込む

既存の HAB 管理画面からアドレスの検索、登録状態の絞り込み、宛先コピーを引き継ぐ。HAB 本体の現行 SQLite host につないで、一覧から接続案内と診断を開けるようにする。 [GUI の製品仕様](../hab-product-spec.md#5-gui仕様)

画面と HTTP の入口を HAB 本体の `src/admin/` に置き、現行の SQLite 版 host の管理関数を呼ぶ。運用者がブラウザから操作しても CLI を使っても、同じ管理処理がアドレスの検証、状態の判定、台帳の更新を行う。画面配信と管理 API は host 上の同じループバック origin に置く。閲覧画面は `npm run hab:dashboard -- --config /path/to/host-config.json` で明示的に起動する。MCP と独立したプロセスで、既存の管理処理を通して SQLite の状態を読む。 [SQLite への移行判断](../hab-decisions.md)

## 登録一覧から始める

```text
登録一覧                                     [エージェントをつなぐ]
検索 [                       ]    登録状態 [すべて]

アドレス            登録        受け取り方     受信箱      会話
helper@demo.hab     承認済み    手動            未読なし    未確認
                    次にすること  [試験メッセージを送る]
```

登録一覧には `hostAdminDoctor` が返す `registration`、`receive`、`reading`、`session` と最初の問題を表示する。行を開くと、それぞれの理由、観測時刻があればその時刻、次の操作が見える。アドレスの検索、絞り込み、コピーは一覧で行う。「エージェントをつなぐ」は製品選択から、新しくつなぎ直すときは該当アドレスの行から始める。 [診断の実装](../../src/host/doctor.ts)

| 段階 | 画面で行うこと | 次に進む条件 |
| --- | --- | --- |
| 製品で接続 | 製品を選び、MCP の接続先と製品レシピの手順を表示する。運用者は製品の画面でコネクタを追加してサインインする。製品で HAB の状態確認を一度実行し、ダッシュボードに戻って「接続を確認」を押す。 | 台帳に使う接続が登録済みで更新が不要なら受け取り方へ進む。新規接続やつなぎ直しでは、承認待ちの申請を確認する。 |
| 承認 | 運用者は申請を選び、新規の HAB アドレスを入力する。つなぎ直しでは一覧で選んだアドレスを使う。申請、アドレス、承認期限を確認して承認する。 | 台帳への登録と紐づけが確定したら「承認済み」を表示する。製品で新しい token が発行される手順と `hab_status` の確認を案内する。 |
| 受け取り方 | レシピに沿って受け取り方を確認し、必要な構成でだけ呼び鈴を設定する。対象アドレスを入れた「AI に渡す文」はコピーできる。 | `doctor` の受け取り方と次の操作を表示する。手動受信なら製品で受信箱を開く案内を出す。定期受信なら製品の予定を確認する案内を出す。 |
| 試験 | 対象アドレスと固定の試験文を確認して「試験メッセージを送る」を押す。`ping` が観測した受付、呼び鈴、受信箱の読み取り、返信を時刻付きで表示する。最後に対象製品で試験メッセージを確認する。 | 会話で確認できたら完了。返信は観測できたときに表示する。呼び鈴を使わない構成には製品で確認する手順を出す。 |

最初の実装では Dots、Grok Bot、Muse、Hermes Desktop、claude.ai を選ぶと、設定手順書の該当箇所が開く。レシピがそろったら、接続案内をそのデータから表示する。製品画面で実行する手順と、HAB 画面で確かめる項目を同じレシピから表示する。画面を開き直したときは host から状態を取り直し、既に承認済みの接続はその続きから進める。試験結果には試験メッセージの観測だけを使い、アドレス全体の最終受信箱読み取り時刻は診断欄に表示する。 [製品別の設定手順](../connections/agent-setup.md) · [レシピと試験の計画](agent-connection-and-receive.md)

## 申請とアドレスを確かめて承認する

承認待ちには、マスク済みの主体、client ID、最初と最後の時刻、回数を表示する。製品名を付けるのは、host が設定から client ID との対応を確かめられるとき。`doctor` の承認待ち表示は一覧への案内に使う。どの申請をどのアドレスに結ぶかは、運用者が申請を照合して選ぶ。申請が見当たらないときは、製品で再度 HAB を呼び出してから一覧を更新する。動的クライアント登録では、製品の認可リクエストにある client ID を申請と照合する。登録された callback URL の集合が対象製品の集合と完全に一致し、実際の redirect URI がその集合に含まれることを確認してから承認へ進む。 [DCR の照合手順](auth0-dcr.md#7-リスクと抑え方)

確認画面には新規登録かつなぎ直しかを明示する。確定時に host が対象を再確認し、申請が期限切れになった場合や対象の登録状態が変わった場合は、最新の情報で選び直す。承認は `pending` と `approve`、却下は `reject` と同じ処理を使う。却下した接続が再びサインインした場合は、新しい申請として一覧に現れる。既存アドレスの権限の引き継ぎと、承認時刻以後に発行された token の条件は管理処理が適用する。 [承認待ちの登録計画](agent-connection-and-receive.md)

承認済みと製品で接続を確認できた状態は別々に出す。古い token を使用中なら製品側での更新を案内する。動的クライアント登録でつなぎ直しが新しい申請を作った場合は、該当する申請の確認に戻る。

## 呼び鈴と試験は対象を確認して操作する

受け取り方は `receive` と同じ処理で設定する。呼び鈴一覧ではアドレス、設定元、ホスト名を見せる。追加では運用者が host 上で用意した登録元の名前を選ぶ。URL と鍵ファイルはサーバー側で解決して `doorbell add` に渡す。この方式なら、Webhook の URL と鍵をブラウザへ渡さずに登録できる。削除では対象を表示して確認する。設定ファイル由来の呼び鈴に戻る場合は、確定する前に表示する。 [呼び鈴の台帳化計画](agent-connection-and-receive.md)

試験は運用者が確定した操作ごとに一通送る。試験結果は `ping` が返したメッセージ ID にひもづける。ページを開く、診断する、更新する操作は読み取りに限る。

## 運用者の権限で操作する

管理サーバーはループバックだけで待ち受ける。閲覧画面は起動ごとに鍵を発行し、運用者だけが読める一時ランチャーでブラウザへ渡す。ブラウザは同じ origin の API への Authorization ヘッダーに使う。承認待ちの詳細と運用操作には専用の権限を割り当てる。HTTP の入口は Host を固定し、変更時に運用者のセッション、Origin、CSRF と対象を確認する。確認ごとに操作 ID を発行し、同じ ID の再送には元の結果を返す。応答が途切れたら元の操作を照合し、確定した証拠がなければ「結果は未確認」と表示する。

画面に返すのは固定の状態、理由、次の操作、許可した観測値。token、鍵、Webhook の URL、本文は host 内に置く。監査には操作者、対象、操作、結果、時刻を残す。 [管理画面の公開範囲と監査](agent-connection-and-receive.md)

## 実装順と受入条件

| 第5段の実装順 | 確かめること |
| --- | --- |
| 登録一覧と製品の案内 | 既存の検索、絞り込み、コピーが使え、5 製品それぞれの設定手順を開ける。対象の `doctor` と画面の4項目が同じ状態を示す。未観測の会話は「未確認」と出る。 |
| 承認待ちと受け取り方 | 運用者が申請を承認・却下し、受け取り方と呼び鈴を画面で設定できる。CLI で見た結果と一致する。承認直後、二重送信、失効、途中で閉じて戻る場合も状態を取り違えない。 |
| 試験と完了 | 運用者が対象製品の会話で最初の一通を確認できる。手動受信と呼び鈴による受信で、受付、呼び鈴、読み取り、返信がそれぞれの証拠どおりに表示される。 |

結合試験では、同じ host の状態を CLI と画面で確認する。匿名や閲覧者の変更要求は拒否され、ループバック外から管理ポートに到達できないことを確かめる。画面、応答、監査に保護対象の値が含まれないことを確認する。実機では、新規接続の運用者が Auth0 のログ調査や台帳の手編集をせず、対象の会話で一通目を確認できるかを確かめる。
