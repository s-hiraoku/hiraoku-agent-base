# Local three-agent integration foundation

The runnable Node and Worker servers still deny every request by default. This revision supplies injectable verification, notification and worker boundaries; it does not connect real agents or register a resident process. Run `npm ci && npm run lint && npm run typecheck && npm test` with Node 26 or newer. All token signing and callback key generation in tests are ephemeral fixtures. No real endpoint, credential, or agent is used.

## Trust boundary

`PinnedJWTVerifier` accepts an operator-pinned RSA public key (RS256, SHA-256, at least 2048 bits), exact issuer/audience/key ID, static subject policy and mandatory active-account resolver. It checks signatures before claims, expiry/nbf/iat, a maximum remaining lifetime of one hour, subject mapping, account status and the intersection of `hub:<operation>` scopes with policy. It rechecks expiry after awaiting account status. It never fetches an attacker-selected key, mints tokens or copies authority from agent names, role claims, reader claims or proxy identity headers. OAuth consent, token issuance, revocation infrastructure, trusted keys and resource metadata remain integration work requiring approval.

Policy separates user requesters/readers, the Hermes worker service and an operator service. User policy cannot grant claim/heartbeat/complete/grants/reconcile. Worker policy requires a runner scope and cannot submit work. `resultReaders` is verifier-owned policy, never task input. Initial submit writes task and reader grants in one atomic batch. Idempotent replay does not restore a revoked reader grant. `revokeReader` records the loss and invalidates subscriptions. Owner reads retain the original task contract; a granted observer's MCP `get` returns only `{id,state,result,at}`. Claim binds execution to the authenticated worker subject and runner scope; another service with the same destination cannot read or mutate its admission.

## MCP and Events

The server uses official `@modelcontextprotocol/server` 2.3.1 and Node HTTP adapter 2.1.1. The pinned SDK 1.32.0 client remains solely for existing legacy client compatibility. The shared factory serves both stateless legacy tools and protocol `2026-07-28`. Events are advertised only when an operator supplies an `EventAPI`. Default entries supply none. The modern test includes required protocol/client-capabilities metadata and matching MCP routing headers.

Authenticated methods are `events/list`, `events/subscribe`, and `events/unsubscribe`, on the same `/mcp` endpoint as the six task tools. Catalog entries include input/payload schemas and webhook delivery. The only event is `task.terminal`; subscription arguments contain a task UUID. Notifications carry exactly `{task_id,state}`. Subscribe returns deterministic principal/task/callback identity, finite `refreshBefore`, `cursor:null`, and `truncated:false`. Lifetimes are one hour by default, at most one day; `ttlMs:null` receives a finite lifetime. Cursor-based history replay is unsupported. Pending terminal outbox records can still be delivered after local interruption or completion-before-subscribe.

`SubscriptionService` requires an explicit active-account resolver, injected encryption key, and operator-owned callback transport factory. Production wiring must use `PinnedCallbackTransport` with an approved exact callback URL set; that transport checks all DNS answers at connection time, connects to a validated public address with the original TLS hostname, refuses redirects, and bounds time/body size. The tests supply offline transports. A client callback URL alone is never approval to allow a network destination.

Callback secrets are AES-GCM ciphertext, bound through authenticated additional data to subscription ID, owner and revision. The key is supplied separately and must survive any approved restart; it is never stored in the Hub database. A replacement secret keeps the previous key encrypted under the new revision and signs with both for at most 30 seconds, bounded also by the old subscription lifetime. Every callback requires a fresh signed single-use challenge or a same-key, same-identity bounded verification cache; refresh does not extend that cache without verification. Verification failures return categorized `-32015` errors without raw request/error data. Every delivery re-verifies the callback conservatively.

Each subscription has its own persistent delivery record; the legacy global outbox acknowledgement is not consumed by this dispatcher. Atomic claims use a 30-second lease and a monotonically increasing fence. Every attempt rechecks account, grant, expiry and subscription revision. Every final write checks both delivery and subscription revisions, fence and unexpired lease. A stale refresh/unsubscribe attempt cannot activate a subscription or commit delivered/dead/pending state. Restart recovers expired attempts with the same event ID, bounded to five total attempts. Transient responses back off; permanent responses including 410/413/redirects stop even during verification. Receivers must deduplicate event IDs because loss of an acknowledgement can produce repeated deliveries. No event path submits a new task.

Authorization is checked immediately before each outbound request. A request that has already begun cannot be retracted by later revocation; subsequent requests and stale acknowledgements are denied. Public deployment still needs an explicit Origin/Host allowlist at the ingress, request/rate limits and approved secret management. The default deny-all endpoint does not claim to implement an OAuth authorization server.

## Worker and reconciliation

`workerLoop` is an explicitly invoked bounded loop, with an adapter factory that can refresh verified runner evidence each cycle, finite idle delay and abort support. Default budget is 100 cycles; maximum is 10,000. It does not install a daemon or create tasks. Errors stop the loop and preserve receipts; operators investigate unknown admissions rather than automatically trying another runner or creating a new run.

`TaskService.reconcile(operator,{id,fence},trustedRuns)` is an internal operator API, not a remote MCP tool. It only frees an unresolved execution slot after querying a known original run ID on the exact original runner boundary, with isolation and durable-idempotency evidence, and confirming the exact fixed successful result. Running/failed/cancelled run responses, guessed run IDs, acknowledgement of a stop request, unknown scopes and stale fences cannot clear the gate. State mutation rechecks original run ID/scope/fence and quarantine/lease expiry atomically after awaiting proof. A cancelled Hub task stays cancelled, with the execution gate closed only after that proof. Legacy records without a bound scope require manual investigation. An adapter clears a cancelled receipt only after the Hub records a closed gate and the exact receipt run/scope matches.

## One bundled approval request before real integration

The following items are requirements for the next concrete connection trial, not actions performed by this revision:

1. Select the Hub's separate private endpoint/transport, such as a new Secure MCP Tunnel. Approve its exact tunnel/project association and Read/Use versus Manage permissions, outbound destination and process lifetime. Do not reuse another application's tunnel identity/key. Sites remains optional and requires its own user/service identity verification before use.
2. Specify the OAuth issuer/resource audience, pinned verification key ID/public key, user subjects, worker subject/runner scope, operator subject and minimal `hub:*` scopes. Approve credential provisioning and protected storage, account revocation resolver and callback encryption key. No secret should be pasted into chat or committed.
3. Approve a personal Hub plugin/MCP registration for Dots and its exact callback destination. Verify that the actual Dots account can discover, subscribe, refresh and unsubscribe Events. Approve only fixed task IDs/state in notifications and fixed output retrieval. The server must fail closed if that account/identity compatibility is absent.
4. Supply only three nonsecret facts for the existing Grok Bot: actual runtime/product/location; supported formal MCP addition/authentication/transport; and whether that same Bot can call MCP during its own tasks. An installed CLI, xAI model API or Cursor Cloud Agents API does not establish this. Approve any actual MCP configuration change separately after the facts resolve the endpoint.
5. Approve the exact isolated Hermes Runs endpoint, dedicated profile/boundary and fixed model, worker credential scope, zero-tool verification and temporary worker lifetime. Do not change the existing Desktop agent, OAuth, cron, mail/calendar jobs or UI. Reuse no credential by copying it without approval.
6. Approve a bounded trial of at most two actual `connectivity_check` tasks (one Dots requester, one existing Grok Bot requester), concurrency one, exactly fixed harmless text, with notifications only to approved Dots callbacks. Specify model-call budget, stop criteria and cleanup. First validate authentication denial, callback lifecycle, restart/receipt reconciliation and revocation with fixtures; no arbitrary input, shell, free destination, personal data or automatic follow-up task is permitted.
7. Only after a separately reviewed trial should a resident process be approved: explicit executable/user/listen address, restart policy, bounded queue/notification retention, storage permissions, shutdown/recovery procedure and operational owner. Source publication and a draft PR do not authorize this or a merge.
