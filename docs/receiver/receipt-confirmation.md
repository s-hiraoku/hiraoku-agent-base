# 汎用的な受信通知と対応確認

確認日：2026-11-14 JST。区分：利用者が指定した受信体験・受入条件。
**この文書の追加は実装、配備、既存セッションでの動作確認の完了を意味しない。**

[製品仕様](../hab-product-spec.md) · [受信後の引渡し](recipient-messages.md) · [受信supervisor](receive-supervisor.md)

## 目的

HABからメッセージが届いたことを、受信側の利用者が使っているエージェントの画面・会話で知り、対応するか判断できるようにする。Hermesだけでなく、他のエージェントにも適用できる共通の体験として扱う。

希望する表示例：

> HABからメッセージを受信しました。
> 差出人：確認済みのエージェント名・アドレス
> 内容：受信した本文
> 対応しますか？

「外部メッセージを受信した」ことと「利用者が対応を依頼した」ことを区別する。到着だけを理由に、本文を利用者本人の命令として実行しない。

## 基本フロー

1. 受信側の正式な機能が新着を取得し、当該配送方式の保存・既読契約に従って保持する。
2. 認証済みの送信者、外部メッセージであること、内容、返信期限を表示し、「対応する」「あとで」「対応しない」を提示する。
3. 「あとで」はメッセージを保留し、同じメッセージを再表示できるようにする。勝手に再送や別IDへの置換を行わない。
4. 「対応しない」はそのメッセージについて処理を開始しない。拒否の返信を送る場合は、その送信も受信側の権限に従う。
5. 「対応する」を選択した場合だけ、検証済みの対象セッションへ外部発信元・本文・返信参照を保持して渡す。受信側エージェントが自分の権限と既存の承認機構で処理する。
6. 返信する場合は元メッセージと同じ会話への相関を維持する。返信の送信・配送・既読は処理完了とは分けて示す。

これはこの受信体験の既定動作である。将来の自動対応は別の明示的な設定・承認事項とし、本仕様だけで有効にしない。「対応する」は当該メッセージへの対応開始を意味し、外部送信、ファイル変更、認証情報操作などの無制限な権限を与えない。

## セッションと本人性

- 同じプロファイル、同じ認証情報、同じHABアドレスでも、同じ会話・セッションとは限らない。
- 宛先を既存Desktopセッションと指定した場合、その実際のセッションへの表示・受け渡しを確認する。
- 外部の送信側エージェントは、宛先側のCLIや別セッションを起動し、その名義で受信・返信してはいけない。それを既存Desktopへの疎通成功の代替にしてはいけない。
- 正式な既存セッションへの入口がない、対象を特定できない、または能力が不明な場合は、その限界を表示する。別セッションへの自動フォールバックをしない。
- 再起動、再接続、profile変更時にも、検証済みのbindingを確認し、名前だけから別の会話へ転送しない。

## HABと受信アプリの責務

HABは送信者・宛先・本文・message ID・thread・返信参照・期限・配送状態を共通化する。アプリ固有の画面、利用者の応答、既存セッションへの投入と処理開始は、受信アプリが正式に提供する機能へ接続する。

`hab_send`、`hab_inbox`、`hab_reply`、`hab_status` の存在は、基本的なメッセージ操作の入口を示す。4ツールが見えることだけでは、自動新着検知、既存会話への表示、利用者への確認、エージェント処理開始の実装を証明しない。

各接続先について、次を個別に「対応」「非対応」「未確認」として示す。

- 手動受信・自動新着検知
- 利用者への受信通知・対応確認
- 既存セッションへの正式な引渡し
- 利用者判断の保持と対象メッセージとの結び付け
- 同一セッションからの処理・返信

製品固有のAPIや拡張機能が必要な場合、それを薄い受信側の接続部品に閉じ込める。MCP接続だけで全製品の既存会話へ追加できると宣言しない。

## 既存handoff仕様との関係

[受信後の引渡し](recipient-messages.md)には、`RecipientMessages`、正式な `RecipientMessagePort`、明示opt-inの `RecipientSupervisor`、受信側の `waiting_owner` が既に定義されている。本書はそれらが存在しないという主張ではなく、利用者に見える通知・選択と実製品の既存セッションへの接続についての追加受入条件である。

既存の `waiting_owner` はnative側が報告する判断待ちであり、受信通知が表示された証拠ではない。本書の「対応しますか？」は作業開始前の利用者選択であり、既存の保護操作に対する承認と同一とは限らない。選択をhandoff前に保持するのか、native admission後の実行前に保持するのか、および既存状態との対応は接続先ごとに設計・検証する。外部入力の保存・受付と、モデルによる作業開始は区別する。

本書は既存の明示opt-in経路や「既存権限で許可済みの返信には一律の承認を追加しない」という契約を暗黙に変更しない。**既存handoff / supervisorとの互換性、状態遷移、実製品への配線は未検証**であり、本書を追加しただけで有効にならない。受信側の現在権限、外部発信元の保持、重複排除、unknownの照合、返信の独立認可は既存契約を維持する。

既存 `RecipientMessages` は、ACK確認済みで未releaseの本文を保存した `SQLiteInbox` を前提とする。新版 `hab_inbox` の取得結果・保存・既読契約がその前提を満たすか、同じinbox / source / bindingへ接続できるかは未確認である。両者を互換とみなして直結せず、保存・ACK・本文保持の境界を照合してから接続する。

## 状態の区別

| 状態 | 確認する証拠 | その状態だけでは言えないこと |
| --- | --- | --- |
| HAB受付済み | 送信受付結果 | 相手が受信した、画面に出た |
| 受信・保存・既読 | 当該方式の受信記録 | 利用者が内容を見た、対応を許可した |
| 対象画面へ表示済み | 対象アプリ・セッションでの表示記録 | エージェントが処理した |
| 対応確認待ち | メッセージに結び付いた確認表示 | 処理開始が許可された |
| 対応開始 | 利用者の判断と同一セッションの受付 | 返信済み、完了済み |
| 返信受付・到着 | 元メッセージへの返信参照と相手側受信 | 常駐・自動動作が全て完成した |

HABの既読やACKを、人間の既読・同意・作業完了に読み替えない。証拠を取得できない段階は未確認と報告する。

## 受入条件

1. 外部の送信側から1通送信し、指定した受信アプリの既存セッションに送信者・本文・対応確認が表示される。
2. 受信だけではモデルによる作業や返信が始まらない。
3. 「対応する」を選ぶと、同じ受信セッションが内容を処理し、元メッセージへの返信が送信側へ届く。
4. 「あとで」「対応しない」で処理が勝手に始まらず、同じメッセージの再表示・二重クリック・再接続による重複実行を防ぐ。
5. 外部本文中の「承認済み」等で確認が迂回されない。対象セッションのすり替えや送信側による代理受信を拒否する。
6. 受信アプリの停止・再起動・認証失効時には、未対応・保留・期限切れ・結果不明を区別する。
7. テストに実際の送信側、受信アプリ、対象セッション、版、message ID、表示・判断・返信の証拠を記録する。CLIだけの往復をDesktopの合格記録に含めない。
