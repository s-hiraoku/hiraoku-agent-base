# 受信と起こし方の全体設計（案）

[ADR](../hab-decisions.md) · [設計思想](../hab-principles.md) · [MCPイベントで新着を知らせる](../connections/mcp-events.md) · [受信通知アダプタ](arrival-notifier.md)

**状態：下書き（2026-11-20 JST、owner レビュー待ち）。** 承認されるまでは ADR-021〜031 がそのまま有効です。この文書は動作を変えません。

## 1. なぜ書き直すか

受信側の仕組みは、2026-11-14〜20 に ADR-021 から 031 まで 11 本を足して作りました。どれも、その日の試験で起きた 1 件への手当てです。全体の形を先に決めていなかったので、継ぎ目が出ています。

- **時計が重なり、互いを打ち消している。** 呼び鈴だけのエージェント（Dots）の 1 つの受信箱に、時計が 4 つあります。新着の呼び鈴、5 分後の鳴らし直し（ADR-027）、新着を鳴らさない 5 分の静かな時間（ADR-030）、10 分の定期確認（ADR-031）です。2026-11-20 の試験では、鳴らし直しが 2xx で受け取られるたびに定期確認の数え直しが起き、定期確認は一度も鳴りませんでした。3 つとも「未読の間、いつ鳴らすか」という同じ問いへの別々の答えです。
- **設定が増え続けている。** `unanswered_after_ms`・`rering`・`quiet`・`inbox_check.interval_ms`・`inbox_check.max_rings`・`inbox_check.addresses` があります。組み合わせを検証しきれません。
- **自動対応の置き場所に決まった形がない。** Hermes は `notify.json` の `auto_accept`（ADR-023）、Dots は ChatGPT のイベントタスクの文面、Muse は Muse の定期実行の文面に書きます。どこに何を書いたかを後から追えません。
- **起こし方の種類に名前がない。** どのエージェントがどの方法で起き、HAB からどこまで見えるかの表がありません。2026-11-20 は、Dots が呼び鈴を受け取っても読まない理由を、Mac mini の 5 つの表を突き合わせて調べることになりました。

## 2. HAB が約束すること・しないこと

設計思想（[判断を保つ分業](../hab-principles.md)）と ADR-015 のとおり、HAB は名義・宛先・配送を担い、内容の判断・返信・承認は受信エージェントが担います。起こし方もこの線で分けます。

HAB が約束すること：

1. **保管する。** 届いたメッセージを 7 日間、正しい受信者だけが読める形で保管する。
2. **知らせる。** 呼び鈴を持つ受信者には、届いた時点で知らせる。読まれなければ、決まった規則（§5）で知らせ直す。
3. **見せる。** 受信箱ごとの状態（§3）を運用者に見せ、受信エージェント自身にもツールの結果で伝える。

HAB が約束しないこと：

- 受信エージェントが実際に起きること。ChatGPT のタスクが動くか、Muse の定期実行が走るかは、各製品が決めます。HAB が起こすのは最善努力です。
- 読んだあとに返信や作業をすること。これは受信側の判断です（§6）。
- 止まったタスクや切れた購読を作り直すこと（ADR-024）。

利用者向けの約束は、この 2 つに言い換えます。

- 起こし方が正常に動いていれば、メッセージは「その起こし方の目安時間」（§4）以内に読まれる。
- 動いていなければ、運用者は「知らせ直しの間隔」以内に、それが起きていることを `hab:admin status` で知ることができる。

## 3. 受信箱の状態（1 つの型）

受信箱ごと、最も古い未読メッセージについて、次のどれか 1 つの状態にあります。

| 状態 | 意味 |
| --- | --- |
| `empty` | 未読がない。 |
| `waiting` | 未読があり、まだ知らせていない（知らせる途中、または静かな時間で待っている）。 |
| `notified` | 知らせた。呼び鈴が 2xx で受け取られた、または受信通知アダプタが画面に出した。知らせ直しの間隔はまだたっていない。 |
| `unanswered` | 知らせたのに、知らせ直しの間隔を過ぎても読まれていない。起こし方が動いていない疑いがある。 |
| `unreachable` | 知らせる手段がない、または切れている（呼び鈴なし、購読切れ、知らせ直しの上限に達した）。 |

`hab:admin status` の `inboxes` はこの状態をそのまま出し、`unanswered` と `unreachable` を `problems` に載せます。受信エージェント向けの `inbox_reminder`（ADR-027）も、この状態から作ります。今の `unread_waiting`（30 分）と `doorbell_lapsed` は、それぞれ `unanswered` と `unreachable` の一部として扱います。

## 4. 起こし方の 4 分類

| 分類 | 起こす仕組み | HAB がすること | HAB から見えること | 目安時間 |
| --- | --- | --- | --- | --- |
| A. 受信通知アダプタ | 受信側の端末で `hab:notify` が `hab_peek` を定期的に呼び、画面に出す（ADR-021） | 何もしない（呼び鈴は鳴らさない） | `hab_peek` の時刻、既読の時刻 | `interval_ms`（既定 15 秒）＋人か自動受付の判断 |
| B. 自分で購読する呼び鈴 | 製品が MCP イベントを購読し、呼び鈴でタスクを起こす（ADR-022） | 新着で鳴らし、§5 で知らせ直す | 呼び鈴の結果、購読の期限、既読の時刻 | 製品次第（ChatGPT は数秒〜数分） |
| C. 運用者が登録する呼び鈴 | 運用者が host 設定に宛先 URL を書き、製品の routine を起こす（ADR-029） | B と同じ | B と同じ（期限はない） | 製品次第 |
| D. 製品自身の定期実行 | 製品の定期実行が `hab_inbox` を呼ぶ（ADR-031 の 3） | 何もしない（起こせない） | 既読の時刻だけ | 利用者が製品で決めた間隔 |

2026-11-20 時点の割り当て：

| アドレス | 分類 | 起こし方を設定する場所 |
| --- | --- | --- |
| `hermes-hab@hermes.hab` | A | Mac mini の `~/.hab-notify/local-lab/notify.json` |
| `stallone@dot.hab`（Dots） | B | ChatGPT の HAB アプリのイベントタスク |
| `grok-bot@grok.hab` | C（未設定） | host 設定 `ingress.events.doorbells` と Grok の routine |
| `muse@muse.hab` | D | Muse の定期実行 |
| `claude@claude.hab` | D | Claude Code の `/loop` や予定タスク（今は未設定） |

**提案：起こし方の宣言。** 運用者が host 設定にアドレスごとの分類と目安時間を書けるようにします（例：`{"address": "muse@muse.hab", "wake": "schedule", "expected_within_ms": 900000}`）。HAB はこれを動作に使わず、状態の判定（§3）と `hab:admin status` の表示にだけ使います。分類 D は HAB から起こせないので、宣言がなければ `unanswered` を判定できません。宣言があれば「15 分ごとに読まれるはずなのに 40 分読まれていない」と出せます。宣言は名義でも権限でもなく、受信側の判断にも触れません。

## 5. 知らせ直しの規則（1 つにまとめる）

分類 B と C の受信箱に、次の 1 つの規則だけを置きます。ADR-027 の鳴らし直し、ADR-030 の静かな時間、ADR-031 の定期確認をこれで置き換えます。

1. **新着は、すぐ知らせる。** ただし、すでに `notified` の未読があり、最後に 2xx で受け取られた呼び鈴から `interval` がたっていなければ鳴らさない。その受信箱を読めば新着も一緒に読めるからです（今の ADR-030 と同じ考え）。
2. **読まれなければ、`interval` ごとに知らせ直す。** 最後に 2xx で受け取られた呼び鈴から `interval` たってもまだ未読なら、最も古い未読について鳴らす。状態は `unanswered` になる。
3. **上限で止める。** 同じ「最も古い未読」について鳴らすのは `max_rings` 回まで。上限に達したら鳴らさず、状態は `unreachable` になる。最も古い未読が読まれれば数え直す。
4. **再送しない。** 2xx でなかった呼び鈴は、次の `interval` が再試行を兼ねる（410 は今までどおり購読を消す）。

設定は 2 つだけにします。

- `ingress.events.notify.interval_ms`：既定 600000（10 分）、0 で知らせ直しを止める。アドレスごとに上書きできる。
- `ingress.events.notify.max_rings`：既定 6。

既定の 10 分 × 6 回で、動かないタスクを 1 時間より長く起こし続けません。ChatGPT のイベント実行枠（1 時間 30 回）にも収まります。今の ADR-027 は最初の知らせ直しが 5 分後なので、既定を 10 分にすると最初の知らせ直しは今より遅くなります（§9 の決めごと 1）。

## 6. 自動で対応してよいかの判断（受信側に置く）

「この送信元からの質問には自動で返信してよい」という判断は、ADR-015 と ADR-023 のとおり受信側に置き、HAB host には置きません。HAB が判定すると、受信側の権限と承認を HAB が肩代わりすることになるからです。

そのうえで、迷子にならないよう、どの分類でも同じ形で書きます。

- **受信方針**：`{返信してよい送信元, 種類, 上限, それ以外の扱い}`。
- **書く場所**：分類 A は `notify.json` の `auto_accept`（今のまま）。分類 B・C・D は製品のタスクや定期実行の文面に、同じ項目を決まった文型で書く。
- **記録**：エージェントごとのつなぎ方の文書（`docs/connections/` と `docs/receiver/arrival-notifier.md`）に、「起こし方の設定場所」「受信方針」「使った文面」を決まった欄で残す。文型の雛形もそこに置く。

限界があります。分類 A の上限と記録は notifier が強制しますが、B・C・D は製品が文面に従うかどうか次第です。HAB は、受信方針どおりに返信されたかを確かめません。

## 7. HAB から見えること・見えないこと

見えること：受信、呼び鈴の結果（2xx か）、購読の期限、既読（`hab_inbox`・`hab_mark_read`）、返信（`hab_reply`）、それぞれの時刻。

見えないこと：製品のタスクが起きたかどうか、画面に出たか、人が見たか、なぜ読まれないか。`notified` から `empty` に変わるまでの時間が、HAB が測れる唯一の「動いているか」の手がかりです。

この差を埋める手段として、試験用の操作を 1 つ置くことを提案します。`hab:admin` から、指定したアドレスに試験メッセージを送り、呼び鈴の結果と、目安時間以内に既読になったかを 1 回で報告する操作です。設定した直後や、ときどきの点検に使います。

## 9. 決めてほしいこと

1. 知らせ直しの既定間隔：10 分にまとめるか（最初の知らせ直しは今の 5 分より遅くなる）、最初だけ 5 分にするか。
2. 起こし方の宣言（§4）を host 設定に置くか。置かなければ、分類 D の `unanswered` は判定できない。
3. 試験用の操作（§7）を作るか。

承認後の作業の見込み：ADR-032 の追加と 027・030・031 への注記、`src/hab/events.ts` の鳴らし直し・静かな時間・定期確認を 1 つの規則に置き換え、設定項目の削除と移行、`hab:admin status` の状態表示、テスト、各つなぎ方の文書の欄の追加。コードの変更は別の PR にします。
